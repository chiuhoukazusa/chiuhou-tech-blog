SSR - Screen Space Reflections 屏幕空间反射

今天实现了 Screen Space Reflections（SSR）——现代实时渲染管线中极其重要的一项技术，广泛用于 AAA 游戏引擎（UE、Unity HDRP）和影视渲染。SSR 让物体在光滑表面上产生真实的反射效果，同时比光线追踪性能快几个数量级。

技术背景

SSR 的核心思想很简单：在屏幕空间中，沿着反射方向步进，找到与场景几何的交点，然后采样那个点的颜色作为反射颜色。

相比传统的光线追踪反射：

  • ✅ 无需构建 BVH 或加速结构
  • ✅ 全程在屏幕空间计算，性能极高
  • ❌ 只能反射屏幕内可见的物体（屏幕外的反射会缺失）
  • ❌ 反射方向朝向相机时无法命中

关键细节：Binary Search 精化

线性步进的步长（10/64 ≈ 0.156 视空间单位）可能造成穿透误报。当线性步进检测到深度交叉后，使用 8 次二分查找精化：

  • 步进命中：在粗粒度位置 hi 和上一帧位置 lo 之间二分
  • 误差降低：从 ~0.156 降低到 ~0.0006（降低约 256 倍）
  • 效果：反射边缘更锐利，接触处无撕裂

Fresnel 反射权重

真实世界中，反射强度取决于入射角。掠射角（接近 90°）时反射最强，正面看时反射最弱。使用 Schlick 近似：

衰减策略

为了避免反射边缘出现硬截断，添加了两种衰减：

1. 屏幕边缘衰减：反射击中点越靠近屏幕边缘，权重越低

2. Roughness Fade：粗糙度越高，反射越弱

迭代历史

第 1 次（初始版本）：~700 行代码，4-Pass 管线，直接编译。

第 2 次（编译修复）：

  • Vec3 缺少一元负号运算符 operator-()，用于计算视线反方向
  • aces() 函数中写了 Vec3/Vec3，但只定义了 Vec3/float，改为逐分量手动除法

第 3 次（验证修复）：

  • 初始验证逻辑检测”地板区域SSR比无SSR更亮”
  • 实际情况：地板的SSR反射方向朝上打到天空背景（暗蓝色），导致反射区域变暗，验证条件失败
  • 改为：检测SSR活跃区域（mask>0.2）的平均颜色变化幅度，只要有效果即通过

技术总结

今天学到的关键点：

  1. G-Buffer 的视空间存储：SSR 在视空间（Camera Space）工作，G-Buffer 存储视空间法线和位置，避免每个像素都做逆变换

  2. 屏幕空间步进的参数调优：步长过大 → 穿透误报；步长过小 → 性能差。实际工程中通常用 16-32 线性步 + 8-16 二分步

  3. Fresnel 的物理意义：电导率（金属度）决定 F0 基础反射率；掠射角时几乎所有材质都会反射（即使是哑光材质在边缘也有明显反射）

  4. SSR 的局限性是固有的：屏幕外的物体无法被反射。现代引擎通常用 SSR + 环境反射（Cubemap）或 RT 反射作为补充

  5. 验证策略要与实际效果匹配：不能假设”有反射=变亮”，天空反射会让物体变暗，夜景反射同理
