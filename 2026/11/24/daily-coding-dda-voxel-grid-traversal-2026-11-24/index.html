DDA 体素网格光线遍历 (Amanatides-Woo)

日拱一卒，功不唐捐。 这是每日编程实践系列的又一篇，今天的主题是 Amanatides-Woo 3D-DDA 体素网格光线遍历 —— 一个看似简单、但在游戏开发和图形学底层无处不在的基础算法。它是体素引擎、体素锥形追踪、阴影查询、遮挡剔除，以及无数 GPU 计算任务的基石。

如果你曾经玩过《我的世界》，或者研究过体素渲染管线，你实际上已经无数次地受益于这个算法，只是它隐藏在海量的着色器和剔除代码深处，很少被单独拿出来讲清楚。

① 背景与动机

1.1 一个朴素但真实的问题

想象这样一个场景：你有一个三维体素网格（voxel grid），比如一个 256×256×256 的离散空间，其中某些单元格被标记为”实心”（固体方块），其余为”空”。现在你从相机的位置发射一条射线，想要知道：

这条射线依次穿过了哪些体素单元格？穿过的第一个实心体素是哪个？

这个问题的答案，直接决定了：

  • 在《我的世界》里，你看向某个方块时，屏幕中央的准星能不能”选中”那个方块；
  • 在体素锥形追踪（Voxel Cone Tracing）里，一条锥形射线会在哪些体素上积累光照信息；
  • 在阴影映射和碰撞检测里，光线能不能被某个固体挡住；
  • 在 GPU 体素化之后的射线 march 里，光线要往哪个方向推进。

这个问题的朴素解法是：把射线在参数区间上分成非常细的很多段，每一段算一次当前点落在哪个体素里，然后把所有不同的体素收集起来。这个做法直观、正确，但它有两个致命缺陷：

  1. 要么漏：如果采样步长太大，射线高速穿过一个很薄的体素时，可能一个采样点都没落在里面，导致漏检；
  2. 要么慢：如果采样步长足够小以保证不遗漏，那么对于一条穿过几百个单元格的长射线，你需要进行成千上万次甚至上百万次的采样和取整运算，绝大多数采样点都落在同一个体素里，做了大量无用功。

这是一种典型的”暴力枚举”思路，它的计算量正比于射线的空间长度，而不是正比于射线实际穿过的体素数量。当射线只是一个像素、而网格却有几亿个体素时，这种浪费是灾难性的。

1.2 学术界给出的答案

1987 年，John Amanatides 和 Andrew Woo 在论文 《A Fast Voxel Traversal Algorithm for Ray Tracing》 中提出了一个优雅的解决方案。这个算法被后人称为 Amanatides-Woo 算法，有时也直接简称为 DDA（Digital Differential Analyzer，数字微分分析器）。

它的核心洞察可以用一句话概括：

与其沿着射线做大量细密的采样，不如解析地算出”射线下一个穿过哪个体素边界”，然后一次跨过一整格。

换句话说，DDA 把”连续空间里的射线”和”离散空间里的体素”用参数化的方式桥接起来：每条射线确定一个参数 t（P(t) = origin + t·direction），而体素的边界对应于一系列精确的 t 值。只要按这些边界 t 值从小到大排序，依次推进，就能不重不漏地访问射线穿过的所有体素。

这个算法的计算量，正比于射线实际穿过的体素数量（而不是射线的长度），其理论复杂度是 O(穿过的体素数)。当射线很陡峭（几乎垂直穿过网格）时，它可能只要几十步；而暴力采样法却无论如何都要跑满预设的采样数。

DDA 不是纸上谈兵，它在真实引擎里长盛不衰：

② 核心原理

这一节是本篇的数学核心。我会从一维讲起，逐步推到二维再推到三维，确保每一步都有直观解释，而不是直接甩结论。

2.1 一维情形：从直觉出发

先看最简单的情况。假设你有一条一维的数轴，数轴上每隔 1 单位有一个”格子边界”，格子编号为 ..., -1, 0, 1, 2, ...。你从位置 o = 0.3 出发，沿着正方向以速度 v = 2（单位/时间）移动。

那么你依次穿过哪些格子的边界呢？

  • 你从 0.3 出发，向右移动到边界 1.0，需要移动 1.0 - 0.3 = 0.7 的距离，耗时 0.7 / 2 = 0.35；
  • 进入格子 1 之后，再向右移动到边界 2.0，需要再移动 1.0 的距离，耗时 1.0 / 2 = 0.5；
  • 以此类推，每跨过一个格子，都固定多花 0.5 的时间。

注意这里非常有规律的两个量：

  • 第一次到达边界的耗时：tMax = (1.0 - 0.3) / 2 = 0.35。这是”距离下一个边界还要多久”。
  • 之后每次跨格的固定耗时：tDelta = 1.0 / 2 = 0.5。这是”每穿过一整个格子要多久”。

这个 tMax 和 tDelta，就是 DDA 算法的全部精髓。在三维里，无非是把三个轴各自的 tMax 和 tDelta 同时维护起来，然后每一步”谁先到边界就推进谁”。

这个循环每一步跨越一个完整的体素，因此总步数恰好等于射线穿过的体素数量，绝不多走，也绝不少走。

2.4 为什么它能做到”不重不漏”？

这是 DDA 最关键的性质，也是它和暴力采样最本质的区别。

不漏（完备性）：射线穿过的每一个体素，都对应着某一段连续的参数区间 [t_entry, t_exit)。当我们按 tMax 从小到大推进时，实际上是在精确地遍历这些区间的边界。只要初始 tMax 计算正确，就没有任何一个区间会被跳过。

不重（无冗余）：每一步推进后，都进入一个全新的体素（相邻体素只共享一个面）。因为 DDA 每次只跨过一个边界，且跨过去之后立刻进入下一个体素，所以同一个体素永远不会被访问两次。

和暴力采样的对比：

  • 暴力采样法：步长固定，有可能跳过薄体素（漏），也有可能在一个大格子内部浪费无数采样点（冗余），两者是矛盾且不可兼得的；
  • DDA：步长是解析地由边界位置决定的，天然做到”恰好访问一次”，既不漏也不重。

这就是为什么 DDA 的理论复杂度是 O(穿过体素数)，而暴力采样是 O(射线长度 / 步长)。

2.5 一个重要的坑：退化情形（棱/角相切）

DDA 有一个经典的口碑：实现起来看着简单，但边界情况极其阴险。

考虑一条射线恰好沿着两个体素的共享面前进，或者恰好穿过一个体素的顶点（角）。此时在数学上，射线同时”距离”两个甚至三个边界一样近，tMax.x 和 tMax.y 可能完全相等。

Amanatides-Woo 的原始实现（6-连通版本）在遇到这种平局时，会只推进其中一个轴，因此它会跳过那些”仅仅被射线擦到一条边/一个角”的对角相邻体素。这在绝大多数应用里是正确且期望的行为——因为我们通常只关心射线真正”进入”的体素，而不是仅仅”擦过”的体素。

但如果你的应用要求26-连通的严格覆盖（比如体素化时不能漏掉任何被穿过的格子），你就需要实现所谓的 supercover（超覆盖） 版本，它在遇到平局时同时推进所有并行的轴，把那些棱/角相切的体素也包含进来。

本篇的验证环节会专门对比这两者的差异，这正是我要强调的”量化验证而非肉眼检查”的价值所在——棱/角退化只影响极少数射线（约 0.5%），靠肉眼看图片永远发现不了，但靠逐格比对就能精确抓到。

3.2 关键数据结构

  • Vec3：一个极简的三维向量结构，只包含加、减、数乘三个操作。DDA 算法本身用到的向量运算非常少，所以不需要引入任何第三方数学库。

  • Cell：一个平凡的 POD 结构 {int x, y, z}，表示体素的整数坐标。之所以用 int 而不是模板化，是因为体素网格坐标天然是整数，而且 int 在 -2^31 到 2^31 范围内足够覆盖绝大多数体素场景（网格边长通常不超过几千）。

  • VoxelTraversal：DDA 算法的封装类，构造函数接收原点 o 和方向 d，traverse(tMax, N) 方法执行遍历并返回结果。把 o 和 d 存在成员变量里，是为了让验证代码可以方便地对同一射线做多次不同 tMax 的遍历。

3.3 与暴力方案的边界划分

为了做严谨的量化验证，我实现了两个基准算法，它们和 DDA 形成对照：

  1. supercover（解析式 26-连通基准）：这是 DDA 的”严格版”，在遇到棱/角相切时同时推进多个轴。它比 6-连通 DDA 多包含一些”擦边”体素。用于验证 DDA 的正确性——任何 DDA 返回的体素，都必须出现在 supercover 里（DDA ⊆ supercover）。

  2. bruteForce（稠密采样基准）：这是朴素的暴力做法，把射线切成 20 万段采样，收集所有被采样点触及的体素。用于验证 DDA 的性能优势——因为它和 DDA 在功能上等价，但计算量完全不同。

这两个基准各司其职：一个管”对不对”，一个管”快不快”。混用它们是错误的（比如用稠密采样去验证正确性，会在大步长下漏检、在小步长下又慢得要死）。

④ 关键代码解析

这一节把核心代码完整贴出来，并逐段解释”为什么这样写”。

4.1 DDA 主体

为什么用 floor 而不是 (int) 强转？ 因为对于负数坐标，(int)(-0.5) 在 C++ 里是向零取整，结果是 0，而正确的体素坐标应该是 -1。std::floor 始终向下取整，与体素坐标的语义一致。这是一个新手极易踩的坑——射线反向穿过网格时，用 (int) 强转会导致第一格就错位。

为什么用 INFINITY？ 当 d.x == 0 时，射线永远平行于 x 轴，永远不会跨过任何 x 方向的边界。给 tDeltaX 赋 INFINITY，就能让它在后续的 min 比较中永远”垫底”，从而被正确地忽略。这比用 if 分支去特判每一条轴要干净得多——一个 INFINITY 哨兵，统一了所有分支。

这里为什么 tMaxX 可能为负？ 这是正常的。当射线沿负方向（stepX = -1）时，nextBoundaryX = x，而 x - o.x 是负数，d.x 也是负数，两个负数相除得到正数。数学上 tMax 必须是非负的”从原点出发还要多久”，因此这个除法天然保证了正负号的正确性——这正是”用参数化而非物理距离”带来的优雅之处。

主循环的几点细节：

  1. 先 push 再判退出：我们要保证射线起点所在的体素一定被记录。所以先无条件 push_back 当前体素，再判断是否需要推进/退出。

  2. tMaxX > tMax && tMaxY > tMax && tMaxZ > tMax 的语义：tMax 是射程上限，三个轴的下一个边界参数都大于射程时，说明射线在射程内不会跨过任何边界，已经到头了。

  3. 三个 if 的优先级：这是一个标准的”取最小”逻辑，但用 if/else if 写而不是 std::min，是为了明确”平局时优先推进哪个轴”——原始 Amanatides-Woo 做法是平局时推进先判断的那个轴（这里偏 x 再偏 y），这决定了 6-连通遍历在退化情形下的具体取舍。

4.2 supercover 基准（26-连通）

supercover 和 DDA 几乎一模一样，唯一的区别在推进那几步：

关键点：eps 的作用。 浮点运算里，两个本应相等的 tMax（比如射线恰好穿过顶点）在计算后可能差一个极小的量（1e-16 级别）。如果不加 eps，std::abs(tMaxX - mn) <= eps 就判定不了这种”几乎相等”的情况，导致 supercover 退化回 6-连通，漏掉擦边体素。eps 取 1e-12 是一个经验值，既足够小（不会误判正常情况），又足够大（能捕获浮点误差）。

为什么 supercover 能作为正确性基准？ 因为 supercover 是 DDA 的”严格超集”：它包含了 DDA 所有会访问的体素，再加上那些被 DDA 在棱/角相切时”合法跳过”的擦边体素。因此正确的判定关系是单向包含 DDA ⊆ supercover，而不是相等。如果反过来要求相等，就会在退化情形下产生大量误报。

4.3 稠密采样基准

这里用 seen 数组去重，是因为同一个体素可能被多个采样点命中，我们只关心”出现了哪些不同的体素”。idx = (x*N+y)*N+z 是把三维坐标拍平成一维索引的经典技巧，避免了使用 std::set 带来的哈希/平衡树开销。

为什么是 20 万步？ 对于射程 tMax = 100 的射线，20 万步意味着步长仅 0.0005，足够密集到几乎不漏任何体素。但代价是巨大的——见性能对比。

4.4 连续性检查

为什么用 Chebyshev 距离 == 1 来检查连续性？ 因为一条射线在三维体素网格里，每跨过一个边界，坐标只会在一个轴上变化 1（6-连通），所以相邻两个体素的 Chebyshev 距离（三个轴坐标差的最大值）必然精确等于 1。如果出现了 > 1，说明 DDA 跳过了中间的体素（漏）；如果出现了 == 0，说明死循环了。这是一个极其廉价的、能同时捕获”漏检”和”死循环”两类 bug 的检查。

⑤ 踩坑实录

这一节记录我在实现全过程中遇到的真实坑。每一个都附上”症状 → 错误假设 → 真实原因 → 修复”的完整链条，希望读者能借此避开。

坑 1：(int) 强转负数坐标导致起点错位

  • 症状：验证报告显示”起点错误射线数”不为 0，且集中在那些沿负方向发射的射线上。
  • 错误假设：我最初以为”世界坐标转体素坐标用 (int)o.x 就够了”，因为体素坐标是整数。
  • 真实原因：C++ 的 (int) 对负数向零取整，(int)(-0.5) == 0，但射线起点 -0.5 实际位于体素 -1 内。于是负方向射线的第一格都被算错了一个位置。
  • 修复：改用 std::floor，它始终向下取整，与体素语义完全一致。

坑 2：错误地用”稠密采样”验证正确性

  • 症状：第一版验证代码用 bruteForce（20 万步采样）作为正确性基准，结果出现 10 条射线”误检”——DDA 返回了 bruteForce 没返回的 cell。
  • 错误假设：我以为采样足够密，bruteForce 的 cell 集合就是”射线穿过的所有 cell”，可以用 相等 来比对。
  • 真实原因：错误的双重叠加。其一，采样法在射线恰好贴着体素面前进时，采样点会全部落在面的某一侧，漏掉另一侧的擦边体素；其二，DDA 是 6-连通，supercover 是 26-连通，二者本就不该”相等”。我用了一个既会漏检、连通性又不对的基准，还用了”相等”这种过严的判定。
  • 修复：把正确性基准换成解析式的 supercover，并把判定从”相等”放宽为”DDA ⊆ supercover“。这是最本质的修复——验证基准必须和被测算法在语义上正确对齐。

坑 3：supercover 不加 eps 导致退化

  • 症状：实现 supercover 后，仍有少量射线在棱/角相切时漏掉了擦边体素，supercover 退化成 6-连通 DDA。
  • 错误假设：我以为浮点除法是精确的，tMaxX 和 tMaxY 在射线穿过顶点时会严格相等。
  • 真实原因：浮点误差让本该相等的两个 tMax 差了 ~1e-16，std::abs(tMaxX - tMaxY) == 0 判定失败，导致 supercover 在”平局判定”上失效。
  • 修复：引入 eps = 1e-12 的容差判定 std::abs(a - b) <= eps，同时保留严格的小于比较作为兜底。

坑 4：性能对比摆错了基准

  • 症状：第二版把性能对比的 bruteForce 换成了 supercover 后，加速比骤降到 1.2x，看起来 DDA “不占优”。
  • 错误假设：我为了图省事，用同一个基准既验正确性又验性能。
  • 真实原因：supercover 和 DDA 是同数量级的算法（都是 O(体素数)），把它当性能基准当然测不出差距。真正能体现 DDA 优势的是稠密采样这种 O(采样数) 的暴力法。
  • 修复：明确分工——supercover 只验正确性，bruteForce 稠密采样只验性能，两个基准各司其职。这是”职责单一”在测试代码里的体现。

坑 5：忘记处理零方向向量

  • 症状：极少数随机生成的射线（方向恰好为 (0,0,0)）导致除零、NaN 传播，最终循环失控。
  • 错误假设：我以为随机方向生成器不会恰好生成全零。
  • 真实原因：虽然概率极低，但 std::uniform_real_distribution 在极端情况（或用户传入固定种子）下完全可能命中。一旦 d 是零向量，1.0/d.x 除零产生 inf，后续比较逻辑混乱。
  • 修复：在 traverse 入口显式检查 if (d.x==0 && d.y==0 && d.z==0) return out;，并在随机生成处对零方向做重采样。防御式编程永远值得。

⑥ 效果验证与数据

这一节给出量化数据，而不是”看起来正确”的截图。全部结果来自程序 stdout，可在本地复现。

6.1 正确性验证结果

解读：

  • 起点错误 = 0：2000 条射线中，DDA 返回的首个体素都精确等于 floor(origin)，起点映射 100% 正确（验证了坑 1 的修复）。
  • 误检 = 0：DDA 输出的每一个体素都落在 supercover 的超集之内，没有任何一个”不属于射线”的体素被错误包含（验证了坑 2 的修复）。
  • 连续性违例 = 0：相邻返回体素的 Chebyshev 距离恒为 1，既无漏检也无死循环（验证了坑 4 的基准选择）。
  • 步数一致性：DDA 平均 46.21 步，与暴力采样收集到的 cell 数一致，说明 DDA 遍历的体素数量是正确的量级。

6.2 性能对比结果

解读：两者遍历的体素数量几乎相同（49.65 vs 49.74），但耗时差了近 700 倍。这是因为暴力采样法做了 20 万次采样和取整，而 DDA 只做了 49 次解析步进。这个加速比会随射程增长而进一步拉大——射程越长，暴力法的固定采样数会暴露得越明显。

6.3 为什么必须量化

封面图展示了 DDA 在二维网格中的遍历路径（金色射线穿过蓝色高亮体素）。但如果只看这张图，你永远无法发现那 5 个坑——尤其是坑 1（负数取整）和坑 2（连通性），它们只影响不到 0.5% 的射线，肉眼看图时会被完全忽略。

这张图只能证明”大概是对的”，量化报告才能证明”精确是对的”。 这正是本系列一贯坚持的”不靠眼睛检查”原则。

⑦ 总结与延伸

7.1 技术局限性

DDA 并非万能，它有明确的适用边界：

  1. 只适用于均匀网格：DDA 的 tDelta 推导依赖于”每个格子边长固定为 1”这个假设。如果你的网格是非均匀的（比如八叉树、KD-Tree 这种自适应结构），你就不能直接套用 DDA，而需要更通用的”相邻边界追踪”（比如对每个轴单独维护边界堆）。

  2. 6-连通 vs 26-连通的选择：默认的 Amanatides-Woo 是 6-连通，它会跳过仅被射线擦边/擦角触碰的对角体素。这在”射线拾取”场景下是对的（我们只关心真正进入的方块），但在”体素化”或”覆盖检测”场景下就是错的。选错连通性，是 DDA 最容易出错、也最隐蔽的地方。

  3. 浮点精度问题：当射线的某个方向分量极小时（比如近乎平行于某个坐标面），tDelta 会变得极大，tMax 的差值会变得极小，浮点误差可能让比较关系翻转。在极端视向（贴近地平线）时，需要额外的稳定化处理。

  4. 不处理”实心体素提前终止”：本篇实现的是”遍历穿过的所有体素”。但实际体素引擎里，我们往往在第一个实心体素处就提前终止（因为方块挡住了）。这个”提前终止 + 最远命中边界”的逻辑需要额外叠加在 DDA 之上，且要注意：终止点可能不是体素的入口，而是射线与实心体的精确交点。

7.2 可继续优化的方向

  • SIMD / GPU 并行化：DDA 天然是”每条射线独立”的数据并行任务，非常适合放到 GPU 的 compute shader 或 CUDA kernel 里批量执行，这是体素锥形追踪在 GPU 上实时运行的基础。

  • 自适应步进：对于稀疏体素网格（大部分是空的），可以先做一次粗粒度的层级遍历（lod 层级体素），快速跳过大片空区域，再在命中的细粒度层级里做精确 DDA。这就是 Octree/Hierarchical-DDA 的思路。

  • 实数精度重构：《A Fast Voxel Traversal Algorithm》的后续研究提出了用纯整数运算重写 DDA 的方法，把浮点 tMax/tDelta 改造成整数连分数表示，从而彻底消除浮点误差和精度漂移，这一点在高分辨率体素下有实际价值。

  • 与距离场结合：如果场景里同时还维护了 SDF（有向距离场），可以用 DDA 做粗步进、用 SDF 做精步进，兼顾”大步跨越”和”精确求交”两种优势。

7.3 与本系列的关联

这篇是图形学/游戏开发方向的一篇，它和本系列之前的若干篇形成了一条清晰的技术脉络：

  • 《Marching Cubes / Marching Tetrahedra》（等值面提取）：解决的是”如何从体素网格里重建表面”，而 DDA 解决的是”如何让一条射线穿过体素网格”，二者是体素渲染管线的一体两面——一个负责”造表面”，一个负责”查体素”。

  • 《SDF Ray Marching》（有向距离场步进）：SDF march 用”距离场给的安全步长”来跳跃，DDA 用”网格边界给的精确步长”来跳跃，本质都是”用解析信息替代盲目的均匀采样”，是同一设计哲学在不同数据结构上的体现。

  • 《Octree / BVH》（空间加速结构）：这些是”非均匀”的加速结构，DDA 是”均匀”网格上的加速结构。理解了 DDA 的”边界参数化步进”，再去看 Octree 的”层级递归下降”，会更容易抓住加速结构的共性。

7.4 一句话总结

DDA 教会我们的事，远不止”怎么遍历体素”——它示范了计算机图形学里最强大的一种思维：当你面对”连续 vs 离散”的边界时，别去暴力采样，而是解析地算出那个边界在哪里，然后一步跨过去。

这种”用解析代替枚举”的思想，从 DDA 到 SDF，从 Shadow Mapping 到 Path Tracing，贯穿了整个实时渲染领域。希望这篇文章能让你在下次遇到”一条线穿过一张网”的问题时，第一时间想到 Amanatides & Woo 在 1987 年给出的那个优雅答案。

背景与动机实时渲染的性能困境现代游戏中，全局光照（Global Illumination, GI）始终是最烧 GPU 的特性之一。一个场景里可能有数十盏灯光，每盏灯都需要进行阴影计算、反射计算、间接光传播……如果全部实时计算，帧率会直接崩塌。 早期 Quake（1996）就面临这个问题：如何让室内场景有逼真的光影，又不破坏流畅的游戏体验？id Software 给出的答案是 Lightmap（光照贴图）——把光照信息预先计算好，存成一张贴图，实时渲染时直接采样贴图，代替实时光照计算。 这个技术在后来的 Quake 2、Half-Life、CS:GO，到 Unity Enlighten、虚幻引擎的 Lightmass，都是核心技术之一。游戏里那种”静态环境的柔和阴影”和”角落里的暗部渐变”，大多数时候是 Lightmap 的功劳，而不是实时 GI。 没有 Lightmap 的痛点没有光照贴图时，常见的替代方案是： 纯环境光：全局加一个常数亮度，没有阴影，平坦无立体感 实时阴影：每帧计算 Shadow Map，开销随光源数量线性增长，多光源场景吃不消 Screen Space GI...
