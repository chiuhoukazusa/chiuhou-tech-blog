布隆过滤器 (Bloom Filter)：用 256KB 替代 7.6MB 的概率型集合

在上一篇关于并查集（Union-Find DSU）的博客里，我探讨了如何用接近 O(α(n)) 的摊还复杂度维护动态连通性。并查集解决的是「两个元素是否在同一集合」的判定问题，它的答案永远是精确的——要么连通要么不连通，不存在灰色地带。

但现实世界里有大量场景，我们其实并不需要一个精确的答案。想象一下这样的需求：你要为 20 亿个 URL 做一个「是否访问过」的标记，用于爬虫去重；或者为 5000 万用户做一个「用户名是否已被注册」的快速预判；又或者在一个只有 256MB 内存的嵌入式路由器上，要过滤掉一个包含 10 万个恶意域名黑名单的请求。如果每个元素都要存储完整的值（比如平均 8 字节的哈希 + 指针开销），内存很快就会爆炸。

这时候，布隆过滤器（Bloom Filter） 登场了。它由一个叫 Burton Howard Bloom 的人在 1970 年提出，核心思想十分朴素却极其深刻：用一小块位数组 + 若干个哈希函数，以允许「假阳性」为代价，换取数量级的内存节省。它是「概率数据结构」的鼻祖，至今仍然是工程界对付「海量元素存在性查询」最趁手的工具之一。

本文将带你从零实现一个布隆过滤器，用 200000 个元素、2M 位的位数组（256KB） 做一次严格的量化验证：证明它零假阴性、假阳性率符合理论公式、内存压缩比高达 30.5 倍。

① 背景与动机

为什么「存在性查询」会成为瓶颈？

我们先退一步，明确一下「存在性查询」到底在问什么。给定一个元素 x，我们想知道 x 是否属于某个已知的集合 S。这是计算机科学里最基础、出现频率最高的操作之一。它的朴素解法有两类，分别对应两个极端：

  1. 精确但费内存：用 std::unordered_set、哈希表、或者数据库的唯一索引。每个元素都要完整存放，附带桶、指针、负载因子带来的额外开销。内存随元素数量线性增长，且常数很大。
  2. 精确但费时间：用排序数组 + 二分查找（O(log n)），或者平衡树（红黑树 / AVL，O(log n)）。时间上有对数开销，但内存仍然要完整存储每个元素。

无论是哪一种，关键瓶颈都在于「必须把元素本身存下来」。一旦元素数量达到「十亿」这个量级，比如：

  • 搜索引擎的 URL 去重集合（Google 每日新增网页数以亿计）
  • 广告系统的「已曝光用户」去重（防止同一广告反复轰炸同一用户）
  • 分布式数据库的 SSTable 读取优化（LevelDB / RocksDB / Cassandra 的布隆过滤器）
  • 比特币节点的轻量钱包（SPV）用它来判断某笔交易是否在区块里
  • CDN 的缓存击穿防护（用布隆过滤器拦截不存在的 key，避免穿透到后端数据库）

在这些场景里，「几百万甚至几十亿元素 × 每个元素几十字节」的内存开销是不可接受的。而更关键的一点是：很多场景其实能容忍「假阳性」。

「假阳性」为什么是可以被容忍的？

「假阳性（false positive）」的含义是：布隆过滤器可能告诉我们「元素 x 在集合里」，但实际上 x 并不在。这个「误报」在工程上通常是无害的，因为它只会导致「多一次多余的确认」，而不会「漏掉一个真实存在」。

以上面的几个场景为例：

  • 爬虫去重：布隆过滤器误报了某个从没访问过的 URL 为「已访问」，后果只是少爬了这一个页面，第二天补爬即可，不会造成数据错误。
  • 用户名预判：误报「用户名已存在」，后果是用户换一个用户名，多一点摩擦，但不会产生「两个用户撞了同一个名字」的脏数据。
  • 缓存穿透防护：误报「key 存在」，后端多查一次数据库，因为数据库里肯定有权威答案，最终结果依然是正确的。

核心洞察：布隆过滤器永远不会漏报真存在的元素（零假阴性），它只可能「多报一些不存在的东西」。而「多报」的代价，往往只是「多问一次权威数据源」这种极其廉价的兜底操作。因此，用「一个可接受概率的假阳性」去换「一个数量级的内存压缩」，是一笔稳赚不赔的买卖。

② 核心原理

位数组：不存元素，只存「指纹的足迹」

布隆过滤器的第一个关键设计是：它根本不存储元素本身，只存储一个 m 位的位数组。

当我们向集合插入元素 x 时，我们并不把 x 的原始字节写进内存。取而代之的是：用 k 个不同的哈希函数，把 x 映射到 [0, m) 这个区间内的 k 个位置，然后把位数组里这 k 个位置全部置为 1。

直观地说，元素 x 在布隆过滤器里的「存在」，不是以 x 本身的形式记录，而是以「位数组上 k 个被点亮的位置」的形式记录的。位数组就像一块黑板，每个插入的元素都往上「涂了 k 个点」。

性质一：零假阴性（Zero False Negative）。 如果元素 x 真的被插入过，那么插入时它已经把 k 个位置全部置为 1 了。查询时，只要哈希函数是确定性的（同一个 x 永远算出相同的位置），那这 k 个位置就依然是 1，查询必然返回真。因此**「在集合中的元素绝不会被漏判为不在」**——这是布隆过滤器能安全使用的根基。

性质二：允许假阳性（False Positive）。 如果 x 没有被插入过，那么它的 k 个位置有可能「恰好」都已经被其他元素（在插入时）置为 1 了。这时候查询会误判为「存在」。这就是假阳性的来源，它的概率就是我们要精确量化和控制的量。

假阳性率的推导：一个概率的故事

现在我们来推导假阳性率 FPR。这是理解布隆过滤器数学本质的核心，我会一步步来，每一步都解释直觉。

第一步：单个位在「插入 n 个元素后」仍然是 0 的概率。

考虑位数组里的某一个固定位置（比如下标 j）。当我们插入一个元素时，它会做 k 次哈希，把 k 个位置置 1。对于位置 j 来说，这次插入「没有碰到它」的概率是多少？

由于哈希函数（在理想情况下）把元素均匀、独立地散布到 [0, m) 的每一位上，那么单次哈希「恰好命中位置 j」的概率是 1/m，因此「没命中位置 j」的概率是 1 - 1/m。

而插入一个元素要做 k 次哈希，这 k 次哈希要全部都没有命中位置 j，这个元素才算「没点亮位置 j」。所以插入一个元素后，位置 j 仍然是 0 的概率是 (1 - 1/m)^k。

接下来，我们插入 n 个元素，一共做了 n · k 次哈希。这 n·k 次哈希要全部都不命中位置 j，位置 j 才能保持为 0。由于各次哈希相互独立，这个概率是 (1 - 1/m)^(n·k)。

直觉：n·k 是总的「哈希次数」，1/m 是每次哈希「点到特定格子」的概率。随着 n·k 增大，某个格子「一直没被点到」的概率就指数地衰减。

第二步：用指数极限化简。

直觉：n·k/m 是「整个位数组的填充密度」——它衡量平均每个格子被点亮了「多少层」。因为总共有 n·k 个「点」要撒到 m 个格子里，平均每个格子被撒中 n·k/m 次。当格子被撒中 λ = n·k/m 次时，一个格子「一次都没被撒中」的概率，恰好就是泊松分布的零项 e^(-λ)。这就是 p = e^(-n·k/m) 的泊松直觉。

第三步：假阳性 = k 个位「全都是 1」。

直觉拆解，这个公式里藏着两个彼此对抗的力：

  • (1 - e^(-n·k/m)) 这一项：它是「单个位已经是 1」的概率。当 k 增大时，元素变多（总哈希次数 n·k 增多），位数组被填得更满，p = e^(-n·k/m) 变小，于是 (1-p) 变大——位数组越满，假阳性越容易发生。
  • k 这个指数：查询时要检查 k 个位。k 越大，需要「恰好全部命中」的位数越多，假阳性越难发生。

所以 k 的作用是双刃剑：增加 k 一方面让查询更「严格」，但另一方面又把位数组填得更满。这两股力量的平衡点，就决定了最优的 k。

为什么用 double hashing 而不是真的造 k 个独立哈希？

理论假设「k 个哈希函数相互独立」。但工程上，真正实现 k 个高质量、相互独立的哈希函数既麻烦又昂贵。一个经典的技巧是 double hashing（双重哈希）：

用两个基础哈希 h1 和 h2，通过线性组合「派生」出任意数量的哈希函数。

这背后的直觉是：h2(x) 作为一个「步长」，让 h1(x), h1(x)+h2(x), h1(x)+2·h2(x), ... 这串下标在 [0, m) 上「走」出一条等差数列。只要 h2(x) 与 m 互素（即 gcd(h2(x), m) = 1），这条数列就能遍历整个区间而不提前重复——这正是我们想要的「k 个位置尽量分散」的效果。

为什么强制 h2 为奇数？ 如果 m 是 2 的幂（本文 m = 2^21），那么任何偶数 h2 都会与 m 有公因子 2，导致 h_i(x) 永远只能落在「同为奇数 / 同为偶数」的那一半下标上，散布质量大打折扣。把 h2 强制设为奇数（| 1），就保证了它与 m = 2^21 互素，从而让双哈希序列覆盖尽可能多的不同位。这是 h2 = mkhash(x, seed) | 1ULL 这行代码背后的数学动机。

至于 h1、h2 本身，我用的是 splitmix64 风格的位混合函数，它把 64 位输入充分「搅拌」，得到雪崩效应良好的输出。细节在代码解析章节展开。

关键数据结构

这个结构体只有一个核心存储：vector<uint64_t> bits。注意它是 64 位整数数组，而不是 vector<bool> 或 bitset。这是有意的：

  • vector<bool> 是陷阱：C++ 标准里 vector<bool> 是做了「位压缩」的特化版本，它把每个 bool 压成 1 bit，导致拿不到普通的 bool& 引用，也无法 &v[i]。它图省内存，但接口诡异，行为与其他 vector<T> 不一致，很多工程团队明确禁用。
  • uint64_t 数组可控：用 bits[(m + 63) / 64] 个 uint64_t 容纳 m 个比特，每个 uint64_t 管 64 个位。置位用 bits[idx >> 6] |= (1ULL << (idx & 63))，读取用 (bits[idx >> 6] >> (idx & 63)) & 1ULL。idx >> 6 是「第几个 uint64_t」，idx & 63 是「这个 uint64_t 里的第几位」。位操作完全透明、可预测。

哈希的职责划分

哈希部分是布隆过滤器的「灵魂」，它决定了位散布是否均匀、假阳性是否贴合理论。我的设计分两层：

  • 底层 mkhash(x, seed)：一个 splitmix64 风格的 64 位混合函数，输入一个 64 位值和种子，输出一个「搅拌充分」的 64 位哈希。反复做「异或 + 右移 + 乘法」，把输入的每一位信息扩散到输出的每一位——这就是「雪崩效应」。
  • 上层 double hashing：insert 和 query 里先算 h1 = mkhash(x, seed1) 和 h2 = mkhash(x, seed2) | 1，再用 h = (h1 + i*h2) % m 依次得到 k 个下标。

职责清晰：mkhash 只负责「把一个值搅匀」，不关心 m、k；double hashing 只负责「用两个搅匀的值铺开 k 个下标」。这种分层让每一部分都容易理解和测试。

为什么这个架构能保证「零假阴性」？

这里我想再强调一次架构上的一个不变量：insert 和 query 用完全相同的哈希函数。插入时把 k 个位置都置 1，查询时检查的是同样的 k 个位置。因此，只要哈希函数是确定性的（没有随机性、没有时间戳、没有内存地址依赖），「插入过」就必然意味着「查询时这 k 个位还是 1」。任何「假阴性」的发生，都只能来自哈希函数的不确定性——而我的 mkhash 是纯函数，double hashing 也是纯函数，所以假阴性在数学上被彻底排除。这个不变量，是布隆过滤器设计里最容易被新手忽略、却最关键的一点。

④ 关键代码解析

这一章我会把所有核心代码完整贴出来，并逐段解释「为什么这样写」。读者完全可以照着复制，自己复现出完全相同的结果。

4.1 位混合函数：splitmix64 风格

为什么这样写？ 布隆过滤器对哈希函数的要求不是「加密安全」，而是两点：快 和 均匀。mkhash 只用 4 次乘法 + 若干次移位异或，非常快；而它采用的「乘法 + 异或 + 移位」组合是著名的 splitmix64 算法，能产生良好的雪崩效应——输入的微小变化会引发输出的巨大差异。

逐行解释：

  • 第一行：0x9E3779B97F4A7C15 是黄金比例 φ = (√5-1)/2 乘以 2^64 的整数表示。把种子乘以黄金比再加到 x 上，给不同种子提供「良好散布」的初始扰动。
  • 第二行 (x ^ (x >> 30)) * 0xBF58476D1CE4E5B9：先把自己的高 34 位「折回来」和低 30 位异或，让高位信息渗透到低位；再乘以一个大奇数（奇数乘法在模 2^64 下是双射，不丢信息）。
  • 第三行：继续用不同移位量（27）和不同奇数乘法搅拌。
  • 第四行：最后再次折叠高位到低位，作为输出。

容易写错的地方：这里的移位量（30、27、31）是 splitmix64 精心选择的，不能随意改。如果你随手改成 x >> 16，雪崩效应质量会显著下降，位散布不均匀，假阳性率会明显偏离理论值。这几个魔数不是「随便挑的」，而是保证哈希质量的「配方」。

4.2 构造函数：分配位数组

为什么 (m + 63) / 64？ 这是向上取整的除 64：m 个比特需要 ceil(m / 64) 个 uint64_t 来装。(m + 63) / 64 用「加 63 再除 64」实现向上取整。比如 m = 2^21 = 2097152，(2^21 + 63) / 64 = 32768，正好 32768 × 64 = 2097152 位，没有浪费。

为什么用 assign 而不是 resize？ assign(count, value) 一次性把数组大小设为 count 并全填 0，对「初始全 0 的位数组」最直接清晰。

4.3 插入操作：置 k 个位

逐行解释：

  • 先算两个基础哈希 h1、h2。种子任意，但必须固定以保证确定性。关键在 h2 末尾的 | 1ULL：强制 h2 为奇数，保证 double hashing 的步长与 m = 2^21 互素，让 k 个下标尽可能分散。
  • h = (h1 + i * h2) % m 是 double hashing 的核心：第 i 个下标 = 起点 h1 + i 个步长 h2，再取模 m。
  • 置位 bits[h >> 6] |= (1ULL << (h & 63))：
    • h >> 6：h 除以 64，得到「第几个 uint64_t」。
    • h & 63：h 模 64（63 = 0b111111），得到「这个 uint64_t 里的第几位」。
    • 1ULL << (h & 63)：把 1 左移到对应位，得到「只有那一位是 1」的掩码。
    • |=：把掩码「或」进目标 uint64_t，把那一位从 0 变 1（幂等）。

为什么用 |= 而不是 =？ 一个位可能被多个元素反复置位（这正是「共享位」的来源）。如果写 =（赋值），后插入的元素可能把之前元素的位「抹掉」，导致假阴性——这是布隆过滤器里绝对致命的 bug。|= 保证置位幂等、只增不减。

4.4 查询操作：检查 k 个位

逐行解释：

  • 哈希计算与 insert 完全一致，这是「零假阴性」的根本保证。
  • 读位 (bits[h >> 6] >> (h & 63)) & 1ULL：先把目标 uint64_t 右移 (h & 63) 位，让目标位落到最低位，再 & 1ULL 提取出 0 或 1。
  • 短路返回：只要任何一个位是 0，立刻 return false（元素必然不在），不用检查剩下的位。这是查询快的原因——「不在集合」的元素往往前几个位就撞到 0，提前返回。
  • 只有 k 个位全部是 1，才 return true（此时是「可能存在」）。

const 的意义：查询不改动状态，声明为 const 成员函数，保证不意外修改位数组，也让 query 可被并发安全地调用（读操作天然线程安全）。

4.5 主实验循环：k 取不同值对比

为什么 m = 1 << 21？ 用 2 的幂（2097152 位 = 256KB）：/64 和 %64 可用位移和掩码优化；更重要的是让「人均位数」r = m/n = 10.48576 是清爽的数值，方便对应理论最优 k ≈ 7。

两套完全不同的查询集：

  • 假阴性测量：遍历所有已插入元素，全都要 query == true。只要有一个返回 false，fn_count > 0，程序立即报错退出。这是「正确性」的硬性门禁。
  • 假阳性测量：遍历所有确定没插入过的元素，统计被误判的数量。这些查询元素与插入集合不重叠（inserted_set.count(v) == 0 显式过滤），保证测到「纯假阳性」。

理论 FPR 的计算：

这是 FPR = (1 - e^(-nk/m))^k 的直接翻译。注意要把整数 n、k、m 显式转成 double 再除法，否则 n*k/m 先做整数除法，结果被截断成 0，exp(0)=1，1-1=0，整个公式就崩了。这是数值计算里经典的「整数除法陷阱」。

4.6 数据准备：保证查询集合「干净」

为什么这么麻烦？ 假阳性率测量要求查询元素「百分百不在集合里」。rng() 生成的随机数理论上可能和 inserted 里某个值重复，不能靠「概率上不会重复」来侥幸。

因此先把 inserted 全部塞进 unordered_set，再继续用同一个 rng() 生成候选值，只有 inserted_set.count(v) == 0（确认不在集合）才收入 query。这个 while 循环保证 query 每个元素都「干净」、确定未被插入，测出的假阳性率才纯粹、可复现。

⑤ 踩坑实录

实现布隆过滤器看起来只有几十行，但这一路我踩了几个典型「看起来对、实则错」的坑，每一个都值得单独记录。

坑 1：vector<bool> 的「位压缩」陷阱

症状：一开始我想当然地用 vector<bool> bits(m, false) 来表示位数组，觉得「它本身就做了位压缩，正好符合我的需求」。结果编译报错——vector<bool> 的 operator[] 返回的是一个代理对象而不是 bool&，无法直接 bits[i] |= something 这类操作，而且取地址 &bits[i] 也会失败。

错误假设：我假设 vector<bool> 和 vector<int> 一样，bits[i] 就是一个可读写的 bool 引用。

真实原因：C++ 标准对 vector<bool> 做了特化，把每个 bool 压成 1 bit，因此它无法提供真正的 bool& 引用，只能用代理对象来模拟读写。这个设计为了省内存牺牲了接口一致性，是 C++ 里著名的「反面教材」。

修复方式：改用 vector<uint64_t> bits，一个 uint64_t 管 64 个位，位操作全部显式写（>> 6、& 63、|=、>> (h & 63)）。这样既高效（每个字节都利用到位），又语法透明、行为可预测。

坑 2：|= 写成 = 导致假阴性

症状：最早的一版代码里，我用 bits[h >> 6] = (1ULL << (h & 63)) 来置位（赋值而非或运算）。跑出来的结果里，fn_count 不为 0——出现了假阴性！

错误假设：我潜意识里觉得「每个元素插入时算出的位都不太会重叠」，用一个位就够了，赋值也没关系。

真实原因：位数组里不同元素完全可能映射到同一个位（这正是布隆过滤器「共享位」的机制，而且 k 越大越常见）。如果用赋值，后插入的元素会把前一个元素在同一个位上「点亮」的记录覆盖掉，导致前面元素的那个位变成 0，查询时就可能因为「某一位是 0」而误判为「不存在」——这就是假阴性，是布隆过滤器绝对禁止的。

修复方式：把赋值改成 |=（按位或），保证置位是幂等的——无论这个位之前是 0 还是 1，置位后都是 1，永不「抹掉」别人的记录。这也是一开始就应该刻进脑子的铁律：布隆过滤器置位只能「或」，不能「赋」。

坑 3：整数除法让理论 FPR 变成 0

症状：算理论假阳性率时，我的第一版代码写的是 exp(-(n * k) / m)，结果 theory_fpr 全是 0，实测 FPR 却正常，两者差了几个数量级，看起来像是「理论完全不对」。

错误假设：我以为 C++ 里 (n * k) / m 会像数学表达式那样先算出浮点结果。

真实原因：n、k、m 都是整数（uint64_t / size_t），所以 (n * k) / m 做的是整数除法，小数部分被直接截断。而 n * k / m 的真实值小于 1（比如 200000 * 7 / 2097152 ≈ 0.667），整数除法把它截断成了 0。于是 exp(-0) = 1，1 - 1 = 0，pow(0, k) = 0——理论 FPR 就恒等于 0 了。

修复方式：把里面的整数显式转成 double 再做除法：exp(-(double)(n * k) / (double)m)。只要任一操作数是浮点，整个表达式就会按浮点运算，0.667 的精度就保留了。这是 C/C++ 里最经典、最高频的「整数除法陷阱」，几乎每个新手做数值计算时都会踩一次。

坑 4：假阳性查询集「不干净」导致 FPR 失真

症状：测量假阳性率时，如果查询集合混入了「其实已经在集合里」的元素，那么这些元素查询必然返回 true（真阳性），会被错误地计进假阳性，让实测 FPR 虚高。

错误假设：我一度觉得「用随机数生成查询集，撞上已插入元素的概率只有 200000/2^64≈0，根本不值得处理」。

真实原因：虽然单次碰撞概率低到可忽略，但程序用的是固定种子的 mt19937_64——它的输出序列是完全确定的。我不能靠「概率上不会重复」这种说辞来保证正确性，而应该用逻辑上的「确定性过滤」来保证。而且「查询集不干净」这个坑一旦踩中，很难从结果上直接看出来（FPR 只偏差零点几个百分点），会让验证结论失去可信度。

修复方式：把 inserted 全部塞进 unordered_set，生成查询元素时用 inserted_set.count(v) == 0 做显式过滤，只有确认不在集合的值才收入 query。这样 query 里每一个元素都「百分百未被插入」，FPR 测量才是纯粹、可复现的。

坑 5：h2 忘记「或 1」导致位散布不均匀

症状：有一版代码里 h2 = mkhash(x, seed2) 没有 | 1ULL，结果实测 FPR 系统性地高于理论值，而且 k 越大偏差越明显。

错误假设：我以为 double hashing 的 h2 只要是「随机值」就够了，奇偶性无所谓。

真实原因：当 m = 2^21（2 的幂）时，如果 h2 是偶数，那么 gcd(h2, m) ≥ 2，h_i(x) = (h1 + i·h2) mod m 这串下标会永远落在同一奇偶性的那一半格子上（因为偶数的倍数的奇偶性不变）。这样「k 个位」实际上只覆盖了位数组的一半，等效于把 m 缩减了一倍，填充密度翻倍，FPR 自然就飙高了。

修复方式：h2 = mkhash(x, seed2) | 1ULL，强制 h2 为奇数。奇数与 2 的幂 m 互素，保证双哈希序列能在 [0, m) 上充分铺开。这是一个「一行代码的修复」，但背后是「互素性决定遍历范围」的数论直觉。

数据解读一：FPR 的「U 型曲线」完美印证最优 k

把上面这组数据画成曲线，你会看到一条清晰的 U 型：

k 理论 FPR 实测 FPR
3 1.5404% 1.5585%

FPR 从 k=3 的 1.54% 一路降到 k=7 的 0.65%，然后又回升到 k=10 的 0.77%。这个「先降后升」的 U 型，正是我在原理章节推导的「k 双刃剑」的直接体现：

  • k 太小（3）：位数组填不满，但查询只检查 3 个位，太「宽松」，容易被撞到 3 个全 1。
  • k 太大（10）：查询检查 10 个位确实严格，但位数组被填得太满（n·k/m = 200000·10/2097152 ≈ 0.95，接近满负荷），单个位几乎全是 1，反而更容易假阳性。
  • k = 7：恰好落在理论最优 k_opt = 7.27 附近，两股力量达到平衡，FPR 最低。

实测值与理论值的相对误差：k=3 时 (1.5585-1.5404)/1.5404 ≈ 1.2%，k=7 时 (0.6875-0.6501)/0.6501 ≈ 5.7%，全部远小于程序里设定的 10% 容差。这说明我的 double hashing + splitmix64 方案非常接近「理想独立哈希」的假设，位散布足够均匀。

数据解读二：零假阴性是「硬保证」，不是「大概」

四组实验（k=3/5/7/10）里，fn_count 全部为 0。也就是说，插入的 20 万个元素，查询时没有一个被漏判。这不是「概率上不太会漏」，而是「逻辑上不可能漏」——因为 insert 和 query 用完全相同的确定性哈希，插入时点的位，查询时必然还在。

这一点是布隆过滤器能用于生产的根本前提。如果假阴性存在，那它就不是「可容忍的误报」，而是「致命的数据丢失」——爬虫会永远跳过某些真实存在的 URL，用户名系统会允许两个用户注册同名。零假阴性是布隆过滤器的底线，任何实现都必须先用这组「遍历所有已插入元素」的测试验证它。

数据解读三：30.5 倍的内存压缩比

内存对比如下：

  • 布隆过滤器位数组：262144 bytes = 256 KB。这是 m/8 = 2097152/8 = 262144 字节，是绝对下界——它只存位，不存任何元素值。
  • unordered_set 估算：8000000 bytes ≈ 7.6 MB。这个估算包含两部分：桶数组（sizeof(void*) × 2n，假设负载因子 0.5）+ 节点开销（每个节点 sizeof(uint64_t) + sizeof(void*) + 8 字节的链表/对齐开销）。
  • 压缩比：8000000 / 262144 ≈ 30.5x。

关键点：这 30.5 倍的压缩比，是用「0.65%～1.56% 的假阳性率」换来的。换句话说，布隆过滤器把「精确集合」的 7.6MB 压成了 256KB，代价仅仅是每查询一个不在集合的元素时，有不到 1% 的概率需要「再问一次权威数据源」来兜底。对绝大多数场景来说，这是极其划算的交易。

而且这个压缩比还会随 n 的增大而越来越夸张：因为布隆过滤器的内存只取决于「你要的误报率」和「总元素数」，不取决于「元素本身的大小」。如果集合元素不是 8 字节的 uint64_t，而是 50 字节的 URL、200 字节的字符串，那 unordered_set 的内存会翻好几倍，而布隆过滤器的位数组完全不变（它根本不看元素长度）。这就是为什么在「超大元素」或「海量元素」的场景里，布隆过滤器的优势是碾压性的。

⑦ 总结与延伸

布隆过滤器的本质

布隆过滤器给我的最大启发，是它是一种「用精度换空间」的思维方式。它没有试图去「更紧凑地存储元素」，而是从根上放弃存储元素，转而存储「元素存在过的痕迹」（k 个被点亮的位），并且坦然地接受由此带来的「可量化、可控制的假阳性」。这种「主动放弃不必要的信息、换取核心诉求的极致优化」的工程哲学，比布隆过滤器这个具体算法本身更值得学习。

技术局限性：什么情况下不适用？

布隆过滤器有三大硬伤，决定了它不能替代真正的集合：

  1. 不支持删除。因为一个位可能是多个元素共享的，你无法安全地把某个位「清零」——那会让其他共享该位的元素一起消失。要支持删除，就得用它的变体 Counting Bloom Filter（把每个位换成计数器，插入 +1、删除 -1），但代价是内存翻若干倍。
  2. 不支持枚举。布隆过滤器存的是「痕迹」，不是元素，你无法从中还原出「集合里到底有哪些元素」。要枚举就必须另存一份真实集合。
  3. 有假阳性。在对精确性有硬性要求的场景（比如金融对账、权限判断），布隆过滤器的误报是不可接受的，必须用布隆过滤器做「预筛」、再用精确结构（哈希表/数据库）做「终审」。

可以继续优化的方向

  1. 最优参数自动求解：本文手工选了 k=7 来讨好理论。工程上应该给定「期望 FPR」和「预估元素数 n」，自动反解出最优的 m 和 k：m = -n·ln(FPR)/(ln2)²，k = (m/n)·ln2，然后向上取整到 2 的幂（方便位操作）。
  2. 分区布隆过滤器（Blocked Bloom Filter）：把大位数组切成多个小块，让 k 个哈希落在不同 CPU 缓存行，显著提升缓存命中率（这是 Google 的 Guava 和 RocksDB 里实际采用的优化）。
  3. 可扩展布隆过滤器（Scalable Bloom Filter）：当元素数量预估不准、单个过滤器快填满时，动态追加新的过滤器，保证 FPR 不随元素增长而失控。
  4. 布谷鸟过滤器（Cuckoo Filter）：支持删除、且在小规模下空间效率更高的同类竞争者，值得作为下一篇的主题对比研究。

与本系列其他文章的关联

  • 哈希函数：本文的 splitmix64 是「非加密哈希」的代表，它追求「快 + 均匀」而非「抗碰撞」。如果读者有兴趣，可以对比我在其他文章里用过的哈希策略，理解「不同场景对哈希的要求截然不同」。
  • 空间换时间 / 精度换空间：本文与之前实现的「并查集」「线段树」「树状数组」共同构成一个主题——如何为「存在性 / 计数 / 聚合」这类基础操作，设计出内存和时间上更极致的数据结构。布隆过滤器是其中「最激进地用精度换空间」的一位。
  • 概率算法：布隆过滤器是「蒙特卡洛式」概率数据结构的入门，它与「拉斯维加斯式」算法（如快排的随机化、Treap 的随机优先级）形成对比：前者可能给出「错误但可检测/可容忍」的结果，后者保证结果正确、只是运行时间随机。理解这两者的区别，是深入算法设计的基石。
