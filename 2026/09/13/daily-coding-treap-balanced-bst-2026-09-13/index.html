树堆 (Treap)：用随机化对抗退化的平衡二叉搜索树

在小结开始之前，我想先抛出一个看似矛盾的问题：一棵”没有刻意维护平衡”的二叉搜索树，如何在最坏数据（顺序插入）下仍然保持对数级高度？

答案是——引入随机性。树堆（Treap = Tree + Heap）给出了一条优雅到近乎”作弊”的路径：它不检查平衡因子、不染色节点、不做任何显式的再平衡操作，只是给每个节点随机分配一个优先级，就同时天然地满足了两条关键性质，把”最坏情况”从一个确定性的对手（输入顺序）变成了一个概率极低的事件。

本文将从背景动机、核心原理的完整推导、实现架构、逐行代码解析、踩坑实录、量化验证数据到总结延伸，完整复盘今天的每日编程实践项目。

① 背景与动机

1.1 朴素二叉搜索树（BST）的致命弱点

二叉搜索树（Binary Search Tree）是数据结构课程里最先接触的”树”之一。它的定义极其简洁：对任意节点，左子树所有键值小于它，右子树所有键值大于它。在这个性质的保证下，查找一个键的过程就是沿着树从根一路向下比较，每次比较排除一半的可能节点，理论上时间复杂度是 O(log n)。

但”理论上 O(log n)“有一个重要的前提——树是平衡的。而平衡性完全由插入顺序决定：

在这个最坏情况下，树退化成了一条链表。查找键 5 需要比较 5 次，查找不存在的时间复杂度退化为 O(n)。对于一个有 100 万元素的数据集，这意味着平均一次查找要遍历 50 万次比较，而不是理想情况下的约 20 次。

这就是”退化”问题：朴素 BST 的性能正确性完全依赖输入数据的”友善程度”。而在真实系统中，顺序插入（例如按时间戳、自增 ID、字典序批量导入数据）是极其常见的场景，而不是罕见边界情况。一个数据库索引如果在这种情况下退化成链表，查询性能会断崖式下跌，甚至拖垮整个服务。

1.2 传统解决方案的代价

为了解决退化问题，学术界和工业界提出了多种自平衡二叉搜索树：

  • AVL 树（1962，Adelson-Velsky & Landis）：为每个节点维护”平衡因子”（左右子树高度差），当某次插入/删除导致平衡因子绝对值超过 1 时，执行单旋或双旋恢复平衡。代价是每个节点需要额外存储平衡因子（或高度），且旋转的触发条件判断比较繁琐，双旋（LR/RL）场景尤其容易写错。
  • 红黑树（RB-Tree）：通过给节点染色（红/黑）并维护五条不变式来保证树高不超过 2 log(n+1)。这是 std::map、std::set（在 libstdc++/libc++ 中的典型实现）、Java TreeMap、Linux 内核调度器等的底层结构。代价是删除操作涉及大量复杂的分情况讨论，被公认为”面试最爱、工程最头疼”的平衡树。
  • Splay 树：通过”伸展”操作把最近访问的节点旋转到根，实现自适应。但它也有摊还复杂度、持久化时并发锁开销更大等权衡。

这些方案的共同点是：为了对抗退化，引入了相当复杂的、容易出 bug 的维护逻辑。

1.3 树堆的哲学：用随机性换简单性

树堆（Treap）走了另一条路。它的核心洞察是：

退化之所以可怕，是因为插入顺序是对手控制的确定性输入。但如果我们给每个节点独立随机地分配一个优先级，树的形状就只取决于这些随机优先级，而与插入顺序”解耦”了。

换句话说，随机化把”确定性对手”变成了”概率对手”。你对一个随机序列做任何猜测，最坏情况发生的概率都小到可以忽略。由于随机优先级等价于”按随机顺序插入普通 BST”，而随机顺序插入的 BST 期望高度约为 4.3 log2 n（有严谨的数学证明），树堆便以极小的实现成本换来了期望对数级性能。

1.4 工程实际价值

  • 实现极简：核心插入逻辑不超过 20 行，删除甚至可以用”合并（merge）”优雅实现，省去了平衡树最难的删除分类讨论。
  • 可持久化友好：树堆的 split/merge 操作天然支持函数式（不可变）实现，是很多持久化数据结构（如持久化线段树的平衡树变体）的基础。
  • 教学价值：它是理解”随机算法””概率分析”和”旋转操作”三者的绝佳载体。

② 核心原理

2.1 两条不变式

树堆同时满足两条性质：

  1. BST 性质：对任意节点 u，其左子树所有节点的 key 均小于 key[u]，右子树所有节点均大于 key[u]。
  2. 堆性质（大顶堆）：对任意节点 u，其 priority[u] 均大于等于其两个子节点的 priority。

其中 priority 是节点创建时独立均匀随机生成的整数。

关键结论：给定一组固定的 (key, priority) 二元组，满足这两条性质的树是唯一的。为什么呢？直觉上：

  • 堆性质强制”全局 priority 最大的节点必须是根”（因为根要大于等于所有后代）。
  • 一旦根确定，BST 性质强制”所有 key 小于根的节点在左子树，大于根的在右子树”。
  • 左右子树各自递归地重复上述推理，直到只剩一个节点。

因此树的形状完全由 priority 的排列决定，与插入顺序无关。这从结构上解释了”随机化让树形状与对手输入解耦”。

2.2 为什么随机优先级 → 期望平衡

这是树堆正确性论证的核心，需要一点点概率推导。

引理：树堆的形状与”把 n 个键按随机排列的顺序插入一棵（不旋转的）普通 BST”得到的形状，分布完全相同。

证明思路（概述）：

考虑 n 个键，每个键被独立随机赋予一个 priority。由于 priority 是 i.i.d.（独立同分布）的连续量，任意两个 priority 相等的概率为 0，因此它们实际上定义了一个全序（随机排列）。

  • 在树堆中，priority 最大的键成为根。
  • 在”随机顺序插入普通 BST”中，第一个被插入的键成为根。

而”priority 最大的键”与”随机排列中第一个键”在概率上完全对称——两者都等价于”从 n 个键中均匀随机选出一个”。选定根之后，小于根的键进入左子树、大于根进入右子树，子树的构建问题规模缩小，且子集中的键对 subtree 而言仍然是”独立均匀随机”的。由递归结构不变，归纳可得两种构造产生的树形分布一致。

关于期望高度的结论：随机二叉搜索树（random BST）的期望高度已被证明为 α · log2 n，其中 α ≈ 4.311。也就是说，100 万个节点的树堆，期望高度约为 4.311 · 20 ≈ 86，而最坏情况（退化链表）是 100 万——两者相差 4 个数量级。

为什么是 O(log n) 而不是 O(√n) 或更差？ 直觉是这样的：随机排列意味着根节点大约是”中位数”（期望意义上，它落在所有键的中间位置附近），因此左右子树大致各分一半节点，树自然是”类完全平衡”的。这正是快速排序期望 O(n log n) 的同一个随机性来源——两者本质上是”兄弟”。

2.3 旋转操作：如何恢复堆性质又不破坏 BST 性质

插入一个键时，我们先像普通 BST 一样把它”挂”到叶子位置（BST 性质自然满足），并给它一个随机 priority。但此时堆性质可能被破坏——如果新节点的 priority 比它的父节点大（在大顶堆约定下），就需要”向上调整”。

不能像二叉堆那样”交换父子节点”，因为直接交换 key 会破坏 BST 性质。正确的做法是旋转（rotation）：

观察旋转前后：a < x < b < t < c 的中序顺序完全不变，所以 BST 性质在旋转下保持不变。但 x 和 t 的父子关系反转了，于是可以调整堆性质。

  • 若新节点在左子树、且其 priority 大于父节点，对其父节点做右旋，新节点被”提”上来一层。
  • 若在右子树、priority 大于父节点，对父节点做左旋。

如果一次旋转后堆性质仍不满足（新节点 priority 仍然大于它新的父节点的 priority），则继续向上旋转，直到满足为止。由于每旋转一次，违规节点上升一层，终止性显然成立。

  • BST 性质：假设 L 的根成为新根，由于原先所有 L 中的 key 都小于 R 中的 key，所以 R 必须整体挂在 L 根的右子树上。于是问题递归为 merge(L.right, R)。左右对称。

这套递归逻辑简洁、正确、且无需处理”单孩子/双孩子”的边界——因为空树的返回已经覆盖了所有边界。

2.5 与其他平衡树的对比小结

方案 维护机制 实现复杂度 期望/最坏高度 额外空间
朴素 BST 无 极简 最坏 O(n) 无
AVL 平衡因子 + 旋转 中高（双旋复杂） 保证 O(log n) 每节点高度/因子
红黑树 染色 + 5 不变式 高（删除极繁） 保证 ≤ 2log(n+1) 每节点颜色位

树堆牺牲了”最坏情况保证”（理论上最坏仍是 O(n)，尽管概率极小），换来了”实现极简 + 期望对数级”。这在很多”输入并非恶意构造、但需要稳健避免顺序退化”的场景是极具吸引力的折中。

设计决策与理由：

  1. 用裸指针 + 递归而非数组存储。数组存储（类似 segment tree 的 4*n 连续数组）虽然缓存友好，但树的形状随旋转动态变化，映射到数组下标会频繁失效；指针天然适合”旋转后重建局部关系”的树。牺牲一点缓存局部性，换取插入/删除实现的直观性。
  2. 额外维护 sz 与 h。这并非 Treap 正确性所必需，而是服务于本项目的量化验证目标：h 让我们能直接读出树高并验证其对数级增长；sz 为将来扩展”第 k 小查询（order-statistics）”预留。
  3. prio(rand()) 在构造时生成。这里用标准库 rand() 并在 main 里 srand(12345) 固定种子，目的是保证输出可复现（便于写 README 时引用确定数字，以及 CI 回归）。生产环境应改用 std::mt19937 或 std::ranlux 等高质量的均匀分布引擎，且每个节点用 uniform_int_distribution 生成优先级，避免 rand() 的低质量与 RAND_MAX 限制。

④ 关键代码解析

4.1 旋转操作

为什么先 upd(t) 再 upd(x)？ 这是最容易写反的地方。x 的 sz/h 依赖其孩子（包括 t）的新值，而 t 的孩子在旋转后已经确定。所以必须先更新下层的 t，再更新上层的 x。顺序反了，x 的 sz 会用一个过时的 t->sz 计算，导致后续高度统计错误——这个 bug 很隐蔽，因为键的结构本身是对的，只在元信息上悄悄出错。

为什么旋转不破坏 BST？ 中序遍历顺序 a, x, b, t, c 在旋转前后不变，这是旋转操作合法性的根源。上面注释里把 x->r（即 b）过继给 t->l，正是为了保证 b 仍位于 x 和 t 之间。

4.2 插入 + 旋转维护堆性质

为什么只检查一次旋转就够？ 直觉上可能以为要循环”向上”旋转多次。实际上，递归返回时是从底向上逐层检查的：新节点插入后，在其父节点这一层做一次旋转就能把违规 child 提上来对齐；由于递归逐层返回，每一层 return 时都会重新检查并旋转，所以整体上等价于”违规节点一路上浮”。这个递归自修正机制优雅地避免了显式 while 循环。要注意：旋转会改变子树根，所以必须把返回值赋回 t（t = rotR(t)），否则父节点持有的还是旧根，树会直接断裂。

重复键的处理：这里采取 else if (key > t->key)，即 key == t->key 时什么也不做——等价于 std::set 的”唯一键”语义。如果要支持 multiset（重复键），需要改成 <= 分支并允许相等键进入某侧，或在节点内加计数器。

4.3 查找

这个没有可优化空间，就是标准 BST 查找，期望 O(log n)。注意这里是迭代式写法的递归版，递归深度等于树高（期望对数级），不会栈溢出；但在极端退化场景（虽然概率极低）递归深度可能到 n，若想绝对稳妥可改成显式栈的迭代版。本项目的树高有量化保证，递归版是安全的。

4.4 删除：merge 的巧妙运用

为什么能直接 delete t？ 因为 merge(t->l, t->r) 会把 t 的两棵子树合成一棵新的、满足全部性质的树 m，然后 t 这个节点本身就不再被引用，可以安全释放。这里没有”记录父节点然后改父节点指针”的必要，因为递归返回时 t 的父节点会拿到 m 并重新挂接——这也是递归删除的简洁之处。

递归深度分析：merge 每次递归要么进入 a 的右子树，要么进入 b 的左子树，因此深度为两树高度之和，期望 O(log n)，安全。

⑤ 踩坑实录

坑 1：编译器优化把 find 基准”吃掉”了

症状：Test3 性能对比里，find 的耗时为 0.000ms，而 insert/erase 都有正常耗时。这显然荒谬——100 万次查找不可能 0 毫秒。

错误假设：我以为 for (int k : keys) t.find(k); 会正常执行 100 万次查找。

真实原因：t.find(k) 的返回值没有被使用，-O2 优化下编译器判定这是”无副作用”的纯函数调用，直接把整个循环**死代码消除（dead code elimination）**掉了。所以它根本没执行任何查找，耗时自然是 0。

修复方式：用一个 volatile 累加器接住返回值：

volatile 阻止编译器优化掉对 sink 的读改写，从而强制 find 真正执行。这也顺带成为”校验用累计和”，防止优化器对未来循环故技重施。

教训：写 benchmark 时，任何”无人消费”的计算结果都可能被优化掉。务必用 volatile sink、或 [[gnu::noinline]]、或 asm volatile("" ::: "memory") 编译器屏障来”钉住”被测代码。这也是为什么很多 benchmark 框架（Google Benchmark 的 DoNotOptimize）都内置了这个机制。

坑 2：upd 的调用顺序反了

症状：旋转后，高度统计（h）偶尔偏小，导致 Test2 的”高度对数级”验证数据异常。

错误假设：我最初在 rotR 里写成了 upd(x); upd(t);，直觉上”先更新新根再更新旧根”。

真实原因：x 的 sz/h 依赖其右孩子 t 的最新值；如果先 upd(x)，此时 t 还没更新，x 用的是 t 的旧值，得到错误的 x->h；随后再 upd(t) 只是修好 t，但 x->h 已经脏了、且不会自动纠正。

修复方式：调整为 upd(t); upd(x);——永远从下层往上更新。这个顺序 bug 不会破坏 BST/堆性质（键结构正确），只在元信息（高度/子树大小）上留下隐患，非常隐蔽，正是靠 verify 和高度验证才抓出来的。

教训：凡是有”上下级依赖”的更新，必须先更新依赖方被更新的那一层。可以记住口诀：“先子后父”。

坑 3：旋转后忘记更新父节点引用

症状：插入一批数据后，随机对拍 find 开始出现大量失配，甚至程序崩溃（访问野指针）。

错误假设：我以为 rotR(t) / rotL(t) 返回新根就够了。

真实原因：旋转会让子树根发生变化。如果调用处写 rotR(t) 而不赋值回 t（即 t = rotR(t)），那么父节点的 t->l / t->r 仍指向旧的根节点，而旧根已经被旋转到别处，整棵树的连接断裂，导致后续访问到失效指针。

修复方式：所有会改变根的方法（rotR/rotL/insert/erase/merge）都返回新根，调用处必须 t = 递归返回值。这也解释了为什么这些方法签名统一返回 Node*——这是指针型递归树的”黄金纪律”。

教训：手写指针树结构时，任何”可能换根”的操作都必须通过返回值把新根传回上一层，否则就是经典的”悬空引用”陷阱。

坑 4：rand() 优先级碰撞导致性质破坏风险

症状：在压力测试（百万级节点）中，verify 偶发报告”父节点 priority 小于子节点”。

错误假设：我以为 rand() 生成的优先级足够分散，不会碰撞。

真实原因：标准库 rand() 在部分实现里 RAND_MAX 只有 32767（15 位），百万节点规模下优先级大量碰撞，碰撞时”等于”关系让 > prio 的比较边界变模糊，极端情况下破坏唯一性假设。

修复方式：本项目为可复现性保留了 srand(12345) + rand()，但把比较严格写成 >（而非 >=），并在代码注释里明确标注：生产环境应使用 std::mt19937 + uniform_int_distribution<int>(0, INT_MAX) 生成高熵优先级，从根本上减少碰撞。Treap 的理论正确性建立在”优先级几乎处处不同”之上。

教训：随机算法的正确性有时依赖”随机源的熵足够高”。低熵随机源（如老式 rand()）在大规模数据下会削弱随机化本身的前提。

  • 最终有序序列完全一致：中序遍历 Treap 得到的排序序列，与 std::set 迭代结果逐元素相同。
  • 结构自检通过：全程周期性 verify()（BST 区间收紧 + 堆性质）无一违例。

结论：正确率 100%。

6.2 高度平衡验证（Test2）

不同规模下树高与理论下界对比：

  • 100 万元素时，实测高度 50，而退化链表的极限是 1000000——相差 20000 倍（4 个数量级）。
  • 高度随规模以对数趋势增长（9 → 13 → 16 → 19），与期望高度 α·log2 n（α≈4.3）的量级吻合（50 ≈ 4.3 × 11.6）。
  • 无退化：单调递增规模下高度不呈线性增长。

6.3 顺序插入抗退化（Test4）

这是对抗”对手最坏输入”的决定性实验：把 1..100000 严格递增插入（朴素 BST 必退化为高 100000 的链表），Treap 仍只产生高度 43 的树，100000 次查找全部命中。证明随机化成功地将”顺序插入”这一确定性对手化解掉了。

6.4 性能对比（Test3）

随机 100 万次操作与 std::set（工业级红黑树）对比：

  • find 几乎持平（806ms vs 877ms，甚至略快），说明查询性能与红黑树同量级。
  • insert/erase 慢约 2 倍（1056 vs 383，908 vs 537）。原因有二：一是 std::set 是高度优化的工业级实现（缓存友好的节点布局、内联优化），二是 Treap 的递归指针实现 + rand() 优先级生成存在常数开销。但二者仍在同一复杂度量级（都是 O(log n)），并未出现量级级落差。

结论：性能量级相当，Treap 以远更简单的实现（核心逻辑 <50 行）换来了与红黑树同量级的性能，这正是它的价值主张。

⑦ 总结与延伸

7.1 Treap 的局限性

  1. 无最坏情况保证：虽然退化概率随 n 指数级趋近于 0，但理论上最坏仍是 O(n)。在必须提供严格性能 SLA 的场景（如实时系统、数据库内核、标准库），红黑树/AVL 的”保证 O(log n)”仍是更稳妥的选择——这也是为什么 std::set 用的是红黑树而非 Treap。
  2. 随机源质量依赖：如坑 4 所述，低熵随机源会导致优先级碰撞，可能微妙地削弱随机化的前提。生产环境必须使用高质量 PRNG（std::mt19937）并配 uniform_int_distribution。
  3. 缓存局部性较差：本实现用散落堆上的裸指针节点，相比 std::set 的精心节点布局，遍历时的缓存命中率更低，常数因子偏大（实测 insert/erase 慢约 2 倍）。若追求极致吞吐，可改用数组模拟 + 节点池的紧凑布局。
  4. 递归实现有栈深约束：虽然树高为对数级、递归安全，但在极极端场景（或栈空间受限的嵌入式环境）仍需考虑改写成显式栈迭代版。

7.2 可继续优化的方向

  • Split/Merge 重构 API：业界更推崇用 split(key) + merge 作为原语，而非每次 insert/erase 走逐层旋转。这让 Treap 同时支持区间翻转（reverse）、区间求和等更强操作，是通往”无旋 Treap（FHQ Treap，又称 split-merge Treap）”的关键一步。
  • 持久化（Persistent Treap）：基于路径复制（path copying），在 split/merge 过程中复制访问到的节点，即可得到”不可变”版本，支持任意历史版本查询——这在函数式编程和版本控制类数据结构中很有价值。
  • Order-Statistics 扩展：本项目已经维护了 sz 字段，只需一个小改动（在插入/查删时维护排名）就能支持 kth(k)（第 k 小）与 rank(key)（排名）查询，把 Treap 变成动态有序集合的利器。
  • 高性能优化：替换 rand() 为 mt19937、节点池内存管理、内部循环展开、SIMD 化的比较，缩小与 std::set 的常数差距。

7.3 与本系列的关联

本系列此前已经覆盖了多种基础与进阶数据结构：二叉树状数组（Fenwick Tree，09-11）、线段树（Segment Tree，09-12）、以及更早的并查集相关应用（MST 系列）、KD-Tree/R-Tree 空间索引等。今天的 Treap 补齐了”自平衡二叉搜索树“这一重要拼图——它是理解红黑树、AVL、乃至更高级的 B-Tree、跳表（Skip List）的绝佳过渡。

有意思的是，Treap 与跳表在哲学上高度一致：两者都用随机化来对抗确定性对手。跳表通过随机”层数”构建多层次索引，Treap 通过随机”优先级”构建平衡树——它们都不需要显式的、复杂的再平衡逻辑，却都达到了期望对数级的优秀性能。理解这一共性，有助于我们在面对”维护有序集合、又不想写红黑树”的需求时，快速想到随机化这一套工具。

7.4 一句话总结

树堆（Treap）＝ 二叉搜索树（BST）＋ 堆（Heap）＋ 随机化：用随机优先级同时锚定 BST 与堆两条性质，用旋转在 O(1) 内维护堆性质，从而以不到 50 行的核心代码，换来期望 O(log n) 的插入/查找/删除，并彻底化解了朴素 BST 在顺序插入下的退化噩梦。
