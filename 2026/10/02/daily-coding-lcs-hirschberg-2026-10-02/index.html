LCS 最长公共子序列 —— 从 O(n·m) 空间到 Hirschberg 线性空间分治

在上一篇文章里，我处理的是”求解偏微分方程”这样一个连续数值问题。今天我们把注意力拉回到离散的、纯算法的世界：最长公共子序列（Longest Common Subsequence，LCS）。这是一个被贴满”经典面试题”标签的问题，几乎每个学过动态规划的人都写过那个朴素的 O(n·m) 二维 DP。但今天这篇文章的真正主角，不是那个朴素的 DP 本身，而是一个让无数人第一次意识到”时间复杂度和空间复杂度是可以被分开优化的“的漂亮算法——Hirschberg 分治算法，它能把 LCS 的空间复杂度从 O(n·m) 压到 O(min(n,m))，同时仍然保留重建出具体子序列的能力。

这篇文章我会完整实现三种算法并严格对比——朴素全表 DP、空间优化的滚动数组 DP、以及 Hirschberg 线性空间分治——然后从”为什么要保留重建能力””滚动数组为什么不够用””Hirschberg 如何用分治把空间压下去”这几个角度，一步步把这道题的深度挖到底。所有结论都用 206 个测试用例 + 子序列性质验证 + 内存 RSS 实测来量化，绝不靠”看起来对”这种感性的判断。

① 背景与动机

1.1 LCS 到底是”哪个”问题？

先把概念钉死，因为”最长公共子串”和”最长公共子序列”是两个完全不同难度的问题，很多初学者在第一步就混淆了：

  • 最长公共子串（Longest Common Substring）：要求两个字符串里连续的一段完全相同。例如 ABCBDAB 和 BDCABA，它们的公共连续片段有 AB、BD、BC 等，最长长度是 2。
  • 最长公共子序列（Longest Common Subsequence）：只要求保持相对顺序，不要求连续。ABCBDAB 和 BDCABA 的 LCS 是 BDAB（长度 4）。你可以看到 B、D、A、B 这四个字符在两个字符串里都按顺序出现了，但它们在原串里并不挨着。

这个”只需要保持顺序、不需要连续”的松弛，正是 LCS 能被动态规划优雅解决、却又在空间上暗藏玄机的根源。

1.2 没有 LCS 会怎么样？——真实世界的入场券

如果你觉得”最长公共子序列”只是算法课本里的一道练习题，那就低估它了。LCS 是**序列比对（sequence alignment）**这个庞大领域的基石。在生物信息学里，DNA/RNA/蛋白质序列本质上就是一串字母（A、C、G、T 或 20 种氨基酸），而”两条基因序列有多少相似度”这个问题，最朴素的度量方式之一就是算它们的 LCS 长度——LCS 越长，说明两条序列越”同源”。

更关键的进阶是：LCS 是编辑距离（Levenshtein distance）的亲兄弟。我在这个系列里（参见 09-05 那篇编辑距离的文章）实现过 Wagner-Fischer 算法，那个问题是”把字符串 A 变成 B 最少需要多少次增删改”。而 LCS 和编辑距离之间有一个漂亮的恒等关系：对于只允许插入和删除（不允许替换）的编辑距离，ED(A, B) = |A| + |B| - 2·LCS(A, B)。也就是说，“有多少字符需要被删除” = “两边总长度减去两倍的最长公共保留部分”。所以每当你做 diff、做版本对比、做文档相似度、做拼写纠错里的模糊匹配，背后都有 LCS（或它的变体）在起作用。

1.3 真正的痛点：空间，不是时间

朴素的 LCS 动态规划，时间复杂度 O(n·m) 已经相当好了（对绝大多数应用场景足够快），但它有一个致命伤：为了最终”重建”出子序列，你必须保存整个 n×m 的 DP 表，因为回溯路径要依赖表中每一个格子的值。

这意味着：当 n = m = 20000 时（这在基因比对、日志 diff、长文本对比里都是很现实的长度），一张 int 类型的 DP 表需要 20001 × 20001 × 4 字节 ≈ 1.5 GB 内存。在桌面环境里，1.5 GB 的内存分配往往直接 OOM（out of memory）崩溃；在嵌入式、移动端、或服务器高并发场景下，这更是完全不可接受的。

于是问题变成了：能不能既保持 O(n·m) 的时间（或者接近它），又把空间压到 O(min(n,m))，同时还不能丢掉”重建出具体子序列”的能力？ 这个问题的答案，就是 Hirschberg 在 1975 年提出的分治算法——它不仅回答了”能”，而且给出了一个优雅到让人拍案叫绝的构造。

1.4 为什么”重建能力”不能丢？

有人可能会说：我只要 LCS 的长度不就够了？为什么非要重建出具体的子序列字符串？

因为在实际应用里，长度只是一个数字，而子序列本身才是结论。做基因比对，你要知道的是”哪一段基因是同源的”，而不是”同源长度是 327 这个数字”。做 diff 工具，你要输出的是”共同的保留行是哪些”，这样才能把差异高亮出来。做拼写纠错，你要知道”删掉哪些字符、保留哪些字符”才能给出建议。一个只能报长度、不能报内容的算法，在这些场景里是半成品。

而朴素 DP 之所以”能重建”，是因为它把整张表都记住了；一旦你为了省空间丢掉这张表，你就丢掉了重建的路径。Hirschberg 的核心价值，就在于它证明了”重建”这件事不需要 O(n·m) 的整表，只需要 O(min(n,m)) 的临时缓冲。

② 核心原理

2.1 问题形式化定义

给定两个字符串：

  • a = a[0..n-1]，长度为 n
  • b = b[0..m-1]，长度为 m

定义一个序列 s 是 a 的子序列，当且仅当 s 可以通过删除 a 中的若干字符（可以删除 0 个，也可以全部删除）得到，且不改变剩余字符的相对顺序。

LCS 问题：求 a 和 b 的一个公共子序列，使得它的长度在所有公共子序列中最大。

形式化的最优子结构可以这样表述：设 L(i, j) 表示 a[0..i) 与 b[0..j)（即前 i 个字符和前 j 个字符）的 LCS 长度，那么：

  • 边界：L(0, j) = 0，L(i, 0) = 0（有一边为空串，公共子序列只能是空，长度 0）。
  • 转移：对于 i ≥ 1, j ≥ 1：
    • 若 a[i-1] == b[j-1]，则 L(i, j) = L(i-1, j-1) + 1
    • 否则 L(i, j) = max(L(i-1, j), L(i, j-1))

这条递推的直觉是：我们同时从两个串的末尾往前看（或从前往后看，对称）：

  • 如果最后一个字符相等（a[i-1] == b[j-1]），那么这两个相等的字符一定可以安全地被同时纳入 LCS（贪心地匹配它们一定不亏，因为匹配它们既不会破坏前面，也不会让结果变短），于是问题规约到”去掉这对相等字符后，前面部分的 LCS 再 +1”。
  • 如果最后一个字符不相等，那么这两个字符不可能同时出现在 LCS 里（因为它们分别在两个串的末尾，谁进了 LCS 另一个就进不了——至少不能同时作为”结尾”匹配）。所以最优解要么舍弃 a 的最后一个字符（L(i-1, j)），要么舍弃 b 的最后一个字符（L(i, j-1)），取两者中更大的那个。

这就是经典到不能再经典的二维 DP 递推。它正确、直观，时间复杂度 O(n·m)，空间复杂度 O(n·m)。

2.2 从”全表”到”滚动数组”：为什么能省空间？

关键观察：在递推公式里，计算第 i 行 L(i, ·) 时，只依赖第 i-1 行的值。也就是说，第 i-2 行、第 i-3 行……那些更早的行，一旦算完了第 i-1 行，就再也不会被用到（对于”只求长度”的场景而言）。

于是我们可以只保留两行：prev（第 i-1 行）和 cur（当前正在算的第 i 行），算完一行后 swap(prev, cur)，把上一行腾出来写下一行。这就是**滚动数组（rolling array）**技巧。

注意我在这里做了一个小优化：主动把较短的字符串放到 a 的位置。因为滚动数组的长度取决于”内层那一维”（这里是 b 的长度 m），我们希望 m 越小越好，所以让 a 是较短的那个，这样 cur/prev 数组的长度就是 min(n,m)+1。这是把空间真正压到 O(min(n,m)) 的关键细节。

但滚动数组有一个致命缺陷：它只能算出”长度”，无法重建出”子序列”。 因为回溯需要知道”在 (i,j) 这个格子，我是从左上走来的、从上面走来的、还是从左边走来的”，而这些方向信息一旦被下一行覆盖，就永久丢失了。你可以在算的时候顺手记下一个”方向矩阵”，但那个方向矩阵的大小又是 O(n·m)，等于又回到了原点——省了表，却没省掉回溯需要的额外信息。

2.3 Hirschberg 的核心思想：分治，而不是回溯

Hirschberg 的洞察非常漂亮。它问了一个看似绕弯的问题：

“重建”这件事，真的需要整张表吗？还是只需要找到”LCS 路径上的一个分割点”就够了？

答案是后者。Hirschberg 用了一个**分治（divide and conquer）**的策略：

  1. 把 a 从中间劈成两半：a = a_left + a_right，其中 a_left = a[0..mid)，a_right = a[mid..n)，mid = n/2。
  2. 找出 b 的一个分割点 k，使得 LCS(a_left, b[0..k)) + LCS(a_right, b[k..m)) 等于最终的 LCS(a, b)。也就是说，完整的 LCS 路径”穿过”了 (mid, k) 这个位置。
  3. 递归地分别求解左边 LCS(a_left, b_left) 和右边 LCS(a_right, b_right) 两段，把两个结果拼接起来就是最终的 LCS。
  4. 递归的每一层，都只用 O(m) 的空间去计算”最后一行”的 DP 值（因为找分割点 k，只需要知道 fwd 和 bwd 这两个长度数组，不需要整张表）。

这个想法之所以能成立，是因为 LCS 满足一个可拆分的性质：如果存在一个最优解，它在 a 的第 mid 个字符处”跨”过了某个 (mid, k) 位置，那么最优解可以分解成”a_left 与 b[0..k) 的 LCS”+”a_right 与 b[k..m) 的 LCS”两段的独立拼接。反过来，只要我们能找到一个”正确的 k”，左右两段各自求最优再拼起来，就整体是最优的。

直觉上：想象完整的 LCS 是 a 和 b 之间的一条”匹配连线”。这条连线在 a 的中间位置 mid 处，一定落在 b 的某一个位置 k 上。我们不需要知道连线的每一段细节，只需要先定位”它在中间这个横截面上的位置 k”，然后递归地去定位左半边、右半边的横截面位置，逐步细化，最终整条连线就被唯一地钉死出来了。而这个”定位横截面位置 k”的操作，每一层都只需要 O(m) 的线性空间。

2.4 如何找到”最优分割点 k”？

这是 Hirschberg 算法里最需要讲清楚的一步。给定当前的子问题 a[alo..ahi) 和 b[blo..bhi)（长度分别为 n、m），我们想知道：把 a 在中间 mid = (alo+ahi)/2 劈开后，b 应该在哪里劈？

我们构造两个长度数组：

  • fwd[k]（forward）：表示 a[alo..mid) 与 b[blo..blo+k) 的 LCS 长度。也就是说，只考虑 a 的左半部分和 b 的前 k 个字符，能匹配多长。
  • bwd[k]（backward）：表示 a[mid..ahi) 与 b[blo+k..bhi) 的 LCS 长度。也就是 a 的右半部分和 b 的后 (m-k) 个字符，能匹配多长。

那么，对于任意一个分割点 k，fwd[k] + bwd[k] 就表示”如果把 b 在 k 处劈开，左 LCS 和右 LCS 的长度之和“。我们遍历 k = 0, 1, ..., m，找到使 fwd[k] + bwd[k] 最大的那个 k，记为 bestk。这个 bestk 就是我们要找的”最优分割点”。

为什么这个 max 一定等于最终的 LCS 长度？ 这是 Hirschberg 正确性的核心，值得展开想清楚：

  • 一方面，任何一个”穿过 mid 横截面的最优解”，必然对应某一个 k，使得左半段的 LCS 长度 + 右半段的 LCS 长度 = 总 LCS。所以 max_k (fwd[k] + bwd[k]) ≥ LCS(a, b)（最优解给出的 k 一定能让等号成立）。
  • 另一方面，fwd[k] + bwd[k] 对任意 k 都不可能超过 LCS(a, b)。因为 fwd[k] 内部已经限定”a 只用到左半、b 只用到前 k”，bwd[k] 限定”a 只用到右半、b 只用后 m-k”，两者对应的字符区间完全不重叠，所以它们拼出来的公共子序列最多只能是 LCS(a, b)（不可能超过全局最优）。所以 max_k (fwd[k] + bwd[k]) ≤ LCS(a, b)。

两边夹逼，max_k (fwd[k] + bwd[k]) = LCS(a, b)。这就是为什么找”使和最大的 k”一定是对的。

2.5 fwd 和 bwd 数组怎么用线性空间算？

回到第 2.2 节，我们已经知道：要算出一段子问题”最后一行的 DP 值”，只需要 O(m) 的滚动数组。而 fwd 恰好就是”a[alo..mid) 对 b[blo..bhi) 的 DP 的最后一行”，bwd 则可以通过把 a 的右半段和 b 的右半段都反转，再算一次”最后一行”得到。

具体来说：

  • fwd[k] = 子问题 a[alo..mid) × b[blo..bhi) 的 DP 表最后一行第 k 列的值，用一次 hirschberg_last_row 就能线性空间算出来。
  • bwd[k] 需要的是 a[mid..ahi) × b[blo+k..bhi) 的 LCS。而 LCS 有一个对称性：LCS(X, Y) = LCS(reverse(X), reverse(Y))（因为反转不改变子序列的”相对顺序”，只是把整条路径镜像了一下）。所以我们把 a[mid..ahi) 和 b[blo..bhi) 各自反转，然后算反转后的 DP 最后一行，就能得到”从右往左”的 LCS 长度分布，进而索引出 bwd[k]。

这样一来，找分割点 k 这一步，总的空间成本就是两个 O(m) 的数组，而不是 O(n·m) 的整表。

2.6 递归结构与空间/时间复杂度分析

空间：Hirschberg 递归的每一层，都只分配几个 O(m) 的临时数组（fwd、bwd，以及反转字符串的副本）。由于递归是深度优先的（先算左半，再算右半），任一时刻只需要保留”当前这层 + 沿调用栈向上的若干层”的缓冲。递归深度是 O(log n)（因为每次 a 被劈半），每层的空间是 O(m)，所以峰值空间仍然是 O(m) = O(min(n,m))（我们让较短的那个当”列方向”）。这就是”线性空间”的来历——它指的是不随 n 增长而增长的那一维。

时间：每一层递归，都要对”a 的一半 × b 的全部”做一次 DP 最后行计算，复杂度是 O(m · n/2)；下一层是 O(m · n/4) + O(m · n/4)（左右两半），再下一层 …… 加起来，每一层的总工作量都是 O(n·m)，一共有 O(log n) 层，所以总时间复杂度是 O(n·m · log n)——这是 Hirschberg 相对朴素 DP 的一个常数因子（log n）的代价，用来换取空间从 O(n·m) 降到 O(m)。

本文的实现里，为了代码清晰，我用了 substr 和 reverse 复制字符串，所以常数会大一些；真正的工业级实现会用索引区间 + 指针来避免复制。这也是第 ⑤ 节”踩坑实录”里会讨论的一个点。

2.7 三种算法的关系一图流

把三种算法放在一起对比，脉络就非常清楚了：

算法 时间 空间 能重建子序列？ 适用场景
朴素全表 DP O(n·m) O(n·m) ✅ n、m 都小，图省事
滚动数组 DP O(n·m) O(min) ❌（只有长度） 只要长度，不要内容
Hirschberg 分治 O(n·m·log n) O(min) ✅ 要内容，且 n、m 大、内存受限

这张表本身就是本文的结论：Hirschberg 是”既要重建、又要省内存”时的唯一选择。 滚动数组省了内存但丢掉了重建；朴素 DP 保住了重建但吃掉了内存；只有 Hirschberg 两者兼得，代价是时间上多一个 log 因子。

2.8 为什么选这三种、而不是别的方案？

可能有人会问：为什么不讲讲”位运算加速的 LCS”（bitset 优化的 O(n·m/word) 时间）、或者”Four Russians”方法（O(n²/log n)）、或者”基于后缀数组/LCP 的近似做法”？答案是：这篇文章的主线是”空间复杂度的权衡”，而不是”时间复杂度的极致优化”。

  • 朴素 DP 是基线参照（baseline），用来验证其他两个算法的正确性——因为它的回溯是”显然正确”的。
  • 滚动数组是展示”省空间的代价”——它是通往 Hirschberg 的台阶，展示了”为什么省空间通常会丢掉重建”。
  • Hirschberg 是正解——它在保留重建能力的同时做到了线性空间。

位运算 / Four Russians 那类技巧虽然能把时间压下去，但它们和”线性空间 + 能重建”这个主线不在同一条思路上，反而会分散焦点。把范围收敛到”三种”而不是”五种十种”，是为了让这篇文章的每一段都有不可替代的教学价值，而不是堆砌名词。

3.2 关键数据结构设计

这个程序里最核心的数据结构其实很朴素，但每个选择都有理由：

  • vector<vector<int>> dp（全表）：朴素 DP 用二维 vector，dp[i][j] 存子问题 a[0..i) × b[0..j) 的 LCS 长度。用 n+1 行 × m+1 列，多出来的第 0 行/第 0 列是”空串”的边界，自然填 0，省去一堆 if 边界判断。
  • vector<int> prev, cur（滚动）：滚动数组用两个一维 vector，prev 是上一行、cur 是当前行。用 swap 而不是重新赋值，是 O(1) 的指针交换，避免逐元素拷贝。
  • vector<int> fwd, bwd（Hirschberg 分割定位）：这两个是长度 m+1 的一维数组，分别存”从左到右”和”从右到左”的 LCS 长度分布，用于定位最优分割点 bestk。它们生命周期很短，用完即弃，这正是线性空间的关键。
  • struct Case { string a, b; int expected_len; }：把测试用例封装成结构体，expected_len 是预先用朴素 DP 算好（随机用例）或手工标定（经典用例）的期望长度。

3.3 Hirschberg 递归内部的”反向反转”技巧

这是整个 Hirschberg 实现里最容易被忽略、却也最容易写错的一个地方。要算 bwd（右半段的 LCS），我需要 a[mid..ahi) 对 b[blo+k..bhi) 的 LCS 长度分布。直接算”从某个中间位置 k 到末尾”的 LCS 很别扭，因为滚动数组天然是从头算到尾的。

解法是利用 LCS 的反转对称性：

把 a[mid..ahi) 和 b[blo..bhi) 各自反转，然后把”反转后的 a 右半”和”反转后的 b 整段”喂给同一个 hirschberg_last_row，得到的最后一行 L'[t] 对应的正是”原问题里，b 从末尾往前数 t 个字符的 LCS 分布”。再经过一次下标翻转，就映射回 bwd[k] = LCS(a[right], b[k..m))。

这个”反转来复用前向 DP”的手法，本质上是用极小的代码成本，把”反向 DP”复用成”正向 DP”，避免单独再写一套从右往左递推的代码。代价是多了两次字符串反转的 O(m) 拷贝，但这个常数开销换来的是代码的简洁和正确性。

3.4 函数职责划分一览

我把代码拆成了职责清晰的几个函数，每个函数只做一件事：

函数 职责
lcs_naive_len 全表 DP，只返回长度（供参照和生成期望值）
lcs_naive 全表 DP + 回溯，返回具体子序列（本文不直接用于验证，留作对照）
lcs_space_len 滚动数组 DP，只返回长度
hirschberg_last_row 计算子问题的”最后一行 DP”，O(m) 空间（是 Hirschberg 的地基）
hirschberg_rec Hirschberg 递归主体：劈半 → 找分割点 → 递归左右 → 拼接
lcs_hirschberg Hirschberg 入口包装函数
is_subseq 验证一个字符串是不是另一个的子序列（结构性验证的核心）
random_string 用 mt19937 生成随机测试串

这种”分成 _len（只求长度）和重建两个版本”的拆分是刻意的：它让”滚动数组只能求长度”这个局限在 API 层面就暴露出来——lcs_space_len 压根没有”重建”的版本，因为做不到。

④ 关键代码解析

这一节我会把核心代码逐块拆开讲，重点是”为什么这样写”，而不是”这行在做什么”。所有代码都能直接复制运行，读者可以跟着走一遍。

4.1 朴素全表 DP：基线参照

这一段的关键设计是”多开一行一列当边界”：dp 是 (n+1) × (m+1)，第 0 行和第 0 列天然是 0，代表”空串”。这样在内层循环里就不用写 if (i==0 || j==0) 的特判，代码干净且不容易错。i 从 1 开始，访问 a[i-1] 是因为 dp 的索引是”长度”，而字符串的索引是”位置”，两者差 1。

为什么这里用 int 而不是 short 或 unsigned char？ 因为 LCS 长度可能很大，short（最大 32767）在 n、m 到 20000 时不够用，而 int 最安全。内存的优化我们交给 Hirschberg 去做，基线参照就求一个”正确且无脑”。

回溯版本 lcs_naive 的思路是：从 dp[n][m] 出发，倒着走。

回溯的每一步都要问：”我当前站在 (i,j)，我是从哪来的？”

  • 如果 a[i-1] == b[j-1]，那么根据递推，这个字符一定是被匹配进 LCS 的（因为相等时我们无条件 +1 并向左上走），把它收进 res，然后同时 --i --j 往左上。
  • 否则，看 dp[i-1][j] 和 dp[i][j-1] 谁大，说明”我是从上面走来的还是从左边走来的”，往值更大的那个方向退。这里用 >= 是为了在两者相等时固定优先往上走，保证行为确定（虽然回溯出的 LCS 可能不唯一，但只要长度对、是公共子序列就行）。

最后 reverse 是因为回溯是从末尾往前收字符，收出来的顺序是反的。这里也是”能重建”的代价所在：整张 dp 表都必须留着，否则回溯走不下去。

4.2 滚动数组 DP：只求长度，O(min) 空间

最容易错的一个点是外层那个 if (a.size() > b.size()) return lcs_space_len(b, a);。很多人写滚动数组时不交换，结果内层数组长度是 m+1（b 的长度 +1），如果 a 比 b 长很多，空间就退化成了 O(max(n,m)) 而不是 O(min(n,m))。交换之后，m 一定是较短的那个，数组长度就是 min(n,m)+1，这才是名副其实的”取 min”。

另一个容易踩的坑是 swap(prev, cur) 之后，cur 里残留的是上一轮的旧值，但下一轮循环会从头开始覆盖 cur[j]（j 从 1 到 m），所以不需要额外清零。但如果你的内层循环是”只更新一部分 j”，就必须小心残留——本文的内层是全量覆盖，所以安全。

这个版本的根本局限显而易见：它只返回 prev[m] 这一个数字。中间所有的方向信息都被覆盖丢弃了，你无法从这个函数里找回”具体是哪条子序列”。这直接引出了 Hirschberg 的必要性。

4.3 Hirschberg 的地基：hirschberg_last_row

这个函数和 lcs_space_len 几乎一样，唯一区别是：它把”最后一行的完整数组” prev 返回出去，而不是只返回 prev[m] 这一个数。这个”最后一行”包含了巨大的信息量——它告诉我们”a[0..n) 和 b 的每一个前缀 b[0..k) 的 LCS 长度分别是多少（k = 0..m）”。这正是 Hirschberg 定位分割点所需要的全部信息。

为什么要单独抽象出这个函数、而不是在 hirschberg_rec 里内联写？ 因为它在递归里会被反复调用（每一层调两次：一次算 fwd，一次算 bwd），抽象出来之后，递归主体就能保持干净，只专注于”劈半、找分割点、递归、拼接”这些高层逻辑。

4.4 Hirschberg 递归主体：心脏

这段递归里有几个必须盯着看的细节，任何一个写错都会导致结果静默错误：

第一个细节：n == 1 的基例。当 a 只剩下一个字符时，我们要做的就是在 b[blo..bhi) 里”从左到右找到第一个等于这个字符的位置”，找到就 push_back 并返回。为什么要”从左到右找第一个”而不是”随便找一个”？因为子序列要保持顺序——如果我们在这层把 a 的这个字符匹配到 b 里靠后的某个位置，就会挤占右侧递归的空间；而匹配到最靠左的位置，能给右侧递归留下最大的自由度。这是一个贪心的正确性保证。

第二个细节：bwd 的下标翻转。hirschberg_last_row(ar, br, ...) 返回的数组 bwd[t]，其中 t 是”反转后 b 里前 t 个字符”的索引，对应原问题里”b 的后 t 个字符”。所以在找分割点时，我们用的是 fwd[k] + bwd[m - k]——注意是 bwd[m - k]，不是 bwd[k]。这个 m - k 的翻转正是”反向数组映射回正向”的关键一步，也是我最容易下意识写错的地方（详见第 ⑤ 节坑 2）。

第三个细节：递归子区间的切分。左递归是 (a, alo, amid, b, blo, blo+bestk)，右递归是 (a, amid, ahi, b, blo+bestk, bhi)。注意左右两半的 a 区间不重叠（[alo, amid) 和 [amid, ahi)），b 区间也不重叠（[blo, blo+bestk) 和 [blo+bestk, bhi)），两半的字符集是不相交的，所以 out 里最后拼出来的字符串不会重复、不会遗漏，且天然保持顺序。

第四个细节：mid 取上取整还是下取整？ 这里 amid = alo + n/2 用的是向下取整。理论上取 alo + (n+1)/2 也正确（只要保证左右两半都比原问题严格更小、能收敛到基例即可）。我用下取整，配合 n == 1 的基例，能保证递归一定终止：因为 n/2 < n（当 n ≥ 2），左右两半的 a 长度都严格小于 n，递归树深度 O(log n)，必达基例。

4.5 入口包装 + 子序列验证

lcs_hirschberg 是一个简单的包装函数，把”整个字符串区间”作为根递归的输入，最终 out 就是重建出的 LCS。

is_subseq 是验证的核心：它用双指针的思想，i 指向 s 待匹配的字符，j（隐含在 for 里）扫过 t。每当 t[j] == s[i] 就 ++i，最后如果 i 走到了 s 的末尾（i == s.size()），说明 s 的所有字符都在 t 里按顺序出现了，即 s 是 t 的子序列。这个验证是 O(|t|) 的，用来确保 Hirschberg 重建出来的字符串真的是公共子序列，而不是”长度恰好对但内容错乱”的假货。

4.6 测试驱动与三路交叉验证

这里随机用例的 expected_len 是用朴素 DP 当场算出来的（lcs_naive_len(a, b)），而不是预先写死的值。这是一个实用的技巧：对于随机数据，与其手写”正确答案”（容易写错、也覆盖不全），不如用”显然正确的参照实现”动态生成期望值。这样测试的覆盖面和可信度都大幅提升。

6 个手工用例则覆盖了几种边界情况：空串（两个都空、期望 0）、经典例子（长度 4）、完全相同的串（长度 = 串长）、全重复字符（aaaaa × aaa = 3）、完全不相交（abc × xyz = 0）、另一个经典例（AGGTAB × GXTXAYB = 4）。这些边界用例是随机数据不容易恰好碰到的，所以必须手工补上。

mt19937 rng(12345) 用固定种子，保证每次运行的结果可复现——这是做性能对比和回归测试的好习惯（如果随机种子是随机的，那么”今天跑了 206 个用例、明天跑了 206 个但内容完全不一样”，无法对比）。

4.7 性能对比的计时手法

有两个细节值得说：

  • volatile int l1：用 volatile 是为了防止编译器把这份计算结果优化掉（因为 l1 后面没被使用，激进优化下编译器可能认为这个计算是”死代码”而删掉）。加上 volatile 强制生成读取代码，保证计时对象真的被算出来了。
  • steady_clock 而不是 high_resolution_clock 或 system_clock：steady_clock 是单调递增的，不会被系统时间调整干扰，最适合做区间计时。system_clock 会被 NTP 校准或手动改时间影响，计时可能为负。

⑤ 踩坑实录

这一节是本文的”避坑指南”，每一个坑都是我实际写代码时踩到、或者意识到”差一点就踩到”的。每条都按”症状 → 错误假设 → 真实原因 → 修复”的结构记录。

坑 1：滚动数组忘记交换长短串，空间退化

  • 症状：写滚动数组时没加 if (a.size() > b.size()) 交换，导致 cur 数组长度是 max(n,m)+1。单个测试看不出问题（因为测试的串都很短），但一分析空间复杂度就发现不是 O(min) 而是 O(max)。
  • 错误假设：”反正滚动数组就两行，长度是 b 的长度，b 和 a 谁长都一样。”
  • 真实原因：滚动数组的”列方向”长度就是另一个字符串的长度。如果不主动把短的放到”行方向”、让长的当”列方向”，数组长度就会取到 max(n,m)，在 n 远大于 m（或反之）时白白浪费空间。
  • 修复：入口处 if (a.size() > b.size()) return lcs_space_len(b, a);，确保 a 是较短的那个，这样数组长度就是 min(n,m)+1。

坑 2：Hirschberg 反向数组的下标翻转写反

  • 症状：找分割点时写成了 fwd[k] + bwd[k]，结果分割点总是偏到边界（k 极小或极大），重建出的 LCS 长度对不上，但又不报错（只是结果错）。
  • 错误假设：”fwd[k] 和 bwd[k] 的 k 语义一样，都是 b 的第 k 个位置。”
  • 真实原因：fwd[k] 的 k 是”b 从前往后数 k 个字符”，但 bwd[k] 是通过反转字符串算出来的，它的 k 是”b 从后往前数 k 个字符”。两者索引方向相反，所以正确的组合是 fwd[k] + bwd[m-k]，其中 bwd[m-k] 表示”b 的后 m-k 个字符”。
  • 修复：把分割循环改成 int val = fwd[k] + bwd[m - k];。这是 Hirschberg 实现里最经典、最高频的错误，建议写的时候就画一张”下标映射图”钉在脑子里。

坑 3：基例 n==1 时，贪心匹配到错误的位置

  • 症状：重建出的 LCS 有时是对的、有时少了字符（尤其当 b 里存在多个相同字符时）。
  • 错误假设：”n==1 时，只要 b 里存在这个字符，随便匹配一个就行。”
  • 真实原因：如果匹配到 b 里靠后的那个相同字符，会”吃掉”本应属于右侧递归的字符位置，导致左右两半贡献的字符在 b 里产生冲突（虽然因为子区间不相交，冲突通常体现在结果变短或破坏顺序）。
  • 修复：n==1 时从左到右找第一个等于 a[alo] 的字符，匹配最靠左的位置，把右侧最大自由度留给右递归。

坑 4：substr 反复复制字符串导致常数爆炸

  • 症状：功能完全正确，但 n=m=2000 的测试里，Hirschberg 反而比朴素 DP 慢不少（本应只慢一个 log 因子）。
  • 错误假设：”substr 和 reverse 只是小开销，可以忽略。”
  • 真实原因：Hirschberg 每层递归都要 substr 复制 a 的一半和 b 的全部，还要 reverse 两个副本。递归有 O(log n) 层，每层都做 O(m) 的复制，累加起来常数因子很大。
  • 修复（本文的取舍）：为了代码可读性，本文保留了 substr/reverse；工业级实现会改用”只传索引区间 + 原地标记反向”来消除复制。这是一个”可读性 vs 常数因子”的经典权衡，我在文末 7.3 会再讨论。

坑 5：随机用例的期望值用手写，结果覆盖不全还写错

  • 症状：最初我想给随机用例也手写期望 LCS 长度，结果既容易算错，又覆盖不到”随机串”里的各种组合。
  • 错误假设：”随机数据也要有’正确答案’才严谨。”
  • 真实原因：随机数据的”正确答案”用朴素 DP 动态生成，既省事又零错误，还能顺带验证朴素 DP 自己（因为它被当成 ground truth）。
  • 修复：cases.push_back({a, b, lcs_naive_len(a, b)}) 用参照实现动态生成期望值，只对少数经典用例手写标定。

6.5 结构性验证的必要性证明

为什么光”三路长度一致”还不够，必须再加 is_subseq？考虑一个理论上的 bug：假设 Hirschberg 在递归拼接时顺序搞反了（比如 out = 右半 + 左半 而不是 左半 + 右半），那么长度依然是对的（因为左右两半的字符数没变），三个实现的长度依然一致，但重建出的字符串已经不是一个合法子序列了。is_subseq 的第四项断言恰好能抓出这种”长度对、内容错”的 bug——这正是”结构性验证”不可替代的地方。

⑦ 总结与延伸

7.1 本文核心收获

这一篇最核心的认知，可以用一句话概括：时间复杂度和空间复杂度是两个可以独立优化的维度，而”重建/回溯”常常是空间复杂度的真正瓶颈。

  • 朴素 DP 为了能回溯，付出了 O(n·m) 的空间。
  • 滚动数组省掉了空间，却也丢掉了回溯能力。
  • Hirschberg 用分治 + “只定位分割点”的思路，在 O(min) 空间下保留了重建能力，代价是 O(log n) 的时间因子。

这种”用分治把’回溯’变成’逐步定位’”的思想，远远超出了 LCS 本身，它是空间压缩类算法的一个通用范式：当你需要追踪一条全局路径、但只想保留 O(线性) 空间时，往往可以”折半定位一个中间点，然后递归”。

7.2 这些方法的局限性

  • Hirschberg 的 O(n·m·log n) 时间：时间上多了一个 log 因子。对”时间敏感、内存宽裕”的场景（比如短串的双重循环），朴素 DP 反而更合适。工具选择要匹配约束，不是越高级越好。
  • 常数因子：本文为了可读性用了 substr/reverse，常数偏大；工业实现需要消除这些复制。
  • 不适用于”近似/模糊”需求：LCS 是精确匹配，对”允许少量错配的模糊比对”，需要转向 Smith-Waterman（局部比对）或编辑距离 + 带 gap 惩罚的序列比对，那些问题比纯 LCS 复杂得多。
  • LCS 不唯一：当存在多个同样长的 LCS 时，Hirschberg（和朴素回溯一样）只会返回其中一个，且具体返回哪个取决于分割点 bestk 的选择策略（本文用 > 取最靠左）。如果需要”所有 LCS”或”字典序最小 LCS”，需要额外的处理。

7.3 可以继续优化的方向

  • 消除字符串复制：把 substr/reverse 换成索引区间 + 反向标记，把常数因子降下来，让 Hirschberg 的时间真正逼近 O(n·m)。
  • bitset 加速：用 bitset 把 DP 的一行压成机器字，做 shift-and 式的 O(n·m/word) 时间优化（Hyyrö 的 bitset-LCS），适合小字母表。
  • 扩展到带权 LCS / 编辑距离：Hirschberg 的思想可以直接套用到”线性空间的编辑距离”上（Myers-Miller 算法），这是把它推广到更通用序列比对的关键一步。
  • 并行化：Hirschberg 的左右两半递归天然可以并行（两半的字符区间不相交，无数据依赖），在 GPU 或多线程下能把 O(n·m·log n) 的墙钟时间进一步压下去。

7.4 与本系列的关联

这篇文章和这一整个”每日编程实践”系列里的几篇形成了清晰的呼应：

  • 09-05 编辑距离（Levenshtein）：LCS 是编辑距离的”只允许删插”特例，ED = |A|+|B|-2·LCS。那篇是 O(n·m) 的 Wagner-Fischer，同样面临空间问题，Hirschberg 思想（即 Myers-Miller）可以直接迁移过去。
  • 09-26 矩阵链乘法：同样是区间 DP + 最优括号化 + 回溯重建，那篇的”重建括号方案”也依赖保存整张 DP 表，和本文的”回溯 vs 分治定位”遥相呼应。
  • 09-07 KMP、09-08 Manacher、09-09 后缀数组：这些是”字符串模式匹配”的另一条线，和 LCS 的”字符串比对”线互为补充——匹配关心”找得到找不到”，比对关心”有多相似”。

字符串这个主题到这里又添了一块重要的拼图：从”匹配”到”比对”，从”要长度”到”要内容”，从”要内容但省内存”到 Hirschberg 分治。下一篇，我会继续在这个方向上深挖，敬请期待。
