马尔可夫链 N-Gram 文本生成 —— 从转移概率矩阵到困惑度

① 背景与动机

你有没有想过，一段看起来”像那么回事”的随机文本是怎么生成的？比如输入法里的联想词、聊天机器人的胡说八道、密码破解里的字典生成器，甚至搜索引擎的拼写纠错——它们的底层都有一个共同的数学工具：马尔可夫链（Markov Chain）。

马尔可夫链的核心思想可以用一句话概括：未来只依赖于现在，而不依赖于过去。用更严谨的数学语言说，一个随机过程的下一步状态，只由当前状态决定，与更早的历史无关。这个性质叫”马尔可夫性”（Markov Property），它把”记住全部历史”这个不可能完成的任务，简化成了”只需要记住上一个状态”。

放到文本生成这个具体场景里，马尔可夫假设就是：下一个字符（或词）只取决于前面几个字符，而不是前面所有字符。这就是 N-Gram 模型。所谓 N-Gram，就是连续 N 个 token 组成的序列。当 N=1 时叫 unigram，只统计每个字符本身出现的频率，生成出来的文本基本是乱码；N=2 时叫 bigram，看前一个字符预测下一个；N=3 时叫 trigram，看前两个字符预测下一个。N 越大，模型记住的上下文越长，生成文本越”像”原文，但同时语料稀疏的问题也越严重。

为什么不用现代的大语言模型，而要学这个”上古”的马尔可夫链呢？原因有三个：

  1. 万亿美元规模的模型都是从它演化来的。Transformer 的注意力机制、GPT 的自回归生成，本质上都是在建模 P(next | 前面所有 token) 的条件概率。而 N-Gram 马尔可夫链是这个思想的最朴素、最透明的实现——没有梯度下降，没有反向传播，你甚至能用一张纸一支笔手算出整个转移概率表。理解它，就理解了语言模型的”地基”。

  2. 工业界仍然在用。移动端输入法（内存受限，跑不了大模型）至今在用它做联想和纠错；DNA 序列比对工具（如 BLAST 的统计打分模型）用 k-mer（生物信息学里的 N-Gram）建模；网络爬虫的 URL 生成、模糊测试（fuzzing）的种子变异，都有它的身影。

  3. 它是理解”困惑度（perplexity）”、”交叉熵（cross-entropy）”这些评价指标的起点。这两个词是现在所有 LLM 论文的标配指标，但它们最早就是定义在 N-Gram 语言模型上的。搞懂了马尔可夫链的困惑度计算，再去理解 GPT 论文里的困惑度，就是水到渠成。

这篇文章会从零开始，用 C++ 实现一个字符级 trigram 马尔可夫链文本生成器，并且——这是本系列一贯的坚持——用数值指标验证模型的正确性，而不是”生成出来的文本看起来像不像”这种主观判断。因为”看起来像”是最靠不住的：一个随机种子生成的东西可能碰巧连贯，也可能碰巧全是乱码，肉眼根本无法给出稳定的结论。

② 核心原理

2.2 状态空间与稀疏存储

把每个不同的 (N-1) 字符上下文看成一个”状态”，那么整个模型就是一个加权有向图：每个状态是一个节点，从状态 A 指向状态 B 的边，权重就是转移概率。

这里有个容易绕晕的地方，需要仔细想清楚：转移不是”从上下文 A 跳到上下文 B”，而是”从上下文 A 生成一个字符，然后用滑动窗口得到新的上下文”。

举个例子，用 trigram（上下文是 2 个字符），当前上下文是 "th"，采样得到下一个字符 'e'，那么输出变成 "the"，新的上下文就是输出末尾的 2 个字符 "he"。所以”生成一个字符”必然导致”上下文右移一位”。这个滑动窗口的机制，是 N-Gram 生成器的核心状态转移逻辑，也是实现时最容易写错的地方之一。

这个图有多少个节点呢？理论上，如果词表大小是 V，上下文长度是 K = N-1，那么最多有 V^K 个可能的上下文。对字符级、V≈27（小写字母+空格）、trigram（K=2）来说，最多 27² = 729 个状态。但实际语料往往只覆盖其中很小一部分——大多数字符组合根本不会出现。所以这个图是极度稀疏的。

稀疏性直接决定了数据结构的选择：不要用 V^K × V 的稠密矩阵（对 5-gram 会爆炸到 27⁴ × 27 ≈ 14 亿，内存无法承受）。正确的做法是用哈希表稀疏存储：

  • 外层 unordered_map<string, ...>：从”上下文字符串”映射到”该上下文下的下一字符计数表”
  • 内层 unordered_map<char, long long>：从”下一字符”映射到”出现次数”

这样只有真正出现过的状态和转移才占用内存。这是典型的时间换空间、稀疏换稠密的工程决策：哈希表让查找是 O(1) 期望复杂度，稀疏存储让内存只随语料的实际复杂度增长，而不是随 V^K 指数爆炸。

2.3 加权随机采样：从概率分布到具体字符

学好了转移概率，下一步就是”怎么按照这个概率去抽一个字符”。这不是”均匀随机数”，而是离散分布采样（discrete sampling）。

最直观也最高效的方法是累积分布函数（CDF）+ 二分查找，俗称”轮盘赌”：

  1. 把该上下文下的每个下一字符，按字符升序排列，计算前缀和，得到累积计数序列 cdf[i]，最后一个元素 cdf[last] = total 就是总计数。
  2. 生成一个 [1, total] 区间均匀分布的随机整数 r。
  3. 用 lower_bound 找到第一个 cdf[i] >= r 的位置 i，对应的字符就是采样结果。

为什么这样能正确采样？直觉是这样的：把区间 [1, total] 想象成一条线段，按每个字符的计数切成若干段，每段的长度正比于该字符的概率。然后在整条线段上均匀地”撒一个点”，这个点落在哪一段，就选中哪个字符。点的落点在各段的概率，恰好就是各段的长度占比，也就是各字符的概率。这就是轮盘赌的几何解释。

这个过程的时间复杂度是 O(log V)（二分查找）。对比另一种方法——遍历所有字符做线性扫描，是 O(V)——在 V 大或者需要大量采样时，CDF+二分有明显的优势。

还有一个实现细节：CDF 必须配合 long long 计数使用，不能直接用浮点概率。原因是浮点累加有精度误差，多次累加后 [1, total] 的整数区间采样能保证精确的正确性，而浮点概率的累加误差可能导致 lower_bound 找到错误的边界。用整数计数做 CDF，再在最后一步”除以 total”转成概率做展示，是更稳健的做法。

怎么理解困惑度这个数？直觉上，困惑度约等于”模型在预测下一个字符时，平均要在一堆选项里犹豫，好像面前平均摆了这么多个等概率的选项一样”。如果模型完美预测（给正确答案的概率是 1），困惑度就是 1；如果模型完全瞎猜，在 V 个字符的词表上均匀随机，困惑度就是 V。所以困惑度越低，模型越好，且困惑度的理论下界是 1，上界（均匀随机）是词表大小 V。

这里有个重要的工程细节：零概率问题。如果某个 (ctx, c) 组合在训练语料里从没出现，MLE 会给它 0 概率，那么 log(0) = -∞，交叉熵直接爆炸。解决办法是平滑（smoothing），最简单的是 Laplace 平滑（也叫 add-1 平滑）：

2.5 为什么不直接用更复杂的模型？

读者可能会问：既然现在有大模型，为什么还要学这个？答案已经在背景里埋下伏笔：马尔可夫链是所有自回归语言模型的”压缩感光底片”。它的优点和缺点都极具教学价值：

  • 优点：无参（除了 N 和平滑系数 α），训练就是一遍 O(L) 的数数（L 是语料长度），内存随语料稀疏增长，生成是 O(L_gen × log V)，完全可解释、可手算、可复现。
  • 缺点：马尔可夫假设本身是错的——真实语言的长程依赖（比如”虽然……但是……”跨越几十个字的呼应）无法被 K=2 的上下文捕捉。这也是为什么 N 要增大，但 N 增大又带来维度灾难（curse of dimensionality）：需要的训练数据随 N 指数增长，否则语料稀疏到每个上下文只出现一次，模型退化成”死记硬背”。

理解这套 trade-off，就是理解了为什么会有 RNN、LSTM、Transformer 这一路演化——它们本质上都是在有限参数下逼近更长的依赖。而困惑度这个指标，从 N-Gram 一路贯穿到了 GPT，是整个故事里不变的那根”线”。

③ 实现架构

3.1 整体数据流

整个程序是一个清晰的四段流水线，每一段都是纯函数式的、可独立验证的：

  • train()：输入语料，输出 Model（unordered_map<context, unordered_map<char, count>>）。
  • normalize()：输入某个上下文下的计数表，输出按字符排序的累积计数数组 CDF 和总计数 total。
  • sample()：输入 CDF + total + RNG，输出采样得到的字符。
  • generate()：输入 Model + 种子上下文 + 目标长度 + RNG，循环”采样 → 追加 → 滑动窗口”，输出生成文本。

3.2 关键数据结构设计

为什么用 string 作为上下文键，而不是自定义的小型结构体？因为对于字符级模型，上下文就是 (N-1) 个字符，直接就是一段短的 string，哈希和比较都自带，零成本。如果未来改成词级模型（上下文是几个词），string 同样适用（词之间加分隔符即可）。

为什么计数用 long long 而不是 int 或 double？两个原因：(1) 整数计数天然避免了浮点累加的精度问题，后面 CDF 采样依赖精确的整数边界；(2) 大语料下计数可能超过 int 的 21 亿上限，long long 更安全。

3.3 采样器与 CDF 缓存

normalize() 函数内部做了几步：先把 CountMap 拷贝到 vector<pair<char,long long>> 做排序（按字符升序，保证 CDF 的确定性），再跑前缀和。这里”按字符排序”是刻意的——它保证了在相同 seed 下、相同的底层分布里，lower_bound 找到的结果是确定的。这个确定性是实现”可复现性验证”（见后文）的基石。

sample() 用 uniform_int_distribution<long long>(1, total) 生成 [1, total] 的均匀整数，再 lower_bound 找边界。注意随机数引擎用的是 mt19937_64（64 位梅森旋转），对于复现实验，固定 seed 就能得到完全相同的序列。

3.5 五个独立验证器的设计

程序里没有”看起来对不对”，而是五个独立的、可打印 PASS/FAIL 的验证器：

  1. 归一化验证：遍历每个上下文，验证其下一字符概率之和 == 1.0（误差 < 1e-9），且总转移次数 == |corpus| - N + 1。
  2. 未登录上下文处理：验证一个从未出现的上下文 "zzz" 不在模型里、生成能优雅停止（不崩溃）。
  3. 可复现性验证：同 seed 跑三次，逐字符比对是否完全一致。
  4. 生成合法性验证：生成文本的每个 N-gram（上下文 + 下一字符）都能在训练语料里查到。
  5. 困惑度验证：计算 Laplace 平滑下的交叉熵和困惑度，验证困惑度 < V+1（即优于均匀随机）。

这五个验证器是本文的”护城河”：它们把”生成文本好不好”这个主观问题，拆解成了五个客观的、可判定的布尔断言。

④ 关键代码解析

4.1 训练：一遍数数建立转移矩阵

为什么窗口是 i + n <= text.size()？ 因为 substr(i, n-1) 需要 i+n-1 都在界内，而 text[i+n-1] 需要 i+n-1 也合法，所以窗口的最后一个合法起点是 text.size() - n。边界条件 i + n <= text.size()（即 i <= size - n）恰好保证取出的窗口完整合法。少算一个字符，转移计数就少了 1，会破坏后面”总转移次数 == 窗口数”的验证。

为什么用 model[ctx][next]++ 而不是显式查找？ 这是 unordered_map 的 operator[] 特性——键不存在时自动插入并零值初始化，再自增。对 “th” 这种上下文，第一次遇到 “e” 时会自动创建 model["th"]["e"] = 0 然后变成 1，第二次遇到变成 2，以此类推。这样把”查找-判断-插入-计数”四步压成一行，代码更简洁，也是 C++ 里处理这种”计数字典”的惯用写法。

4.2 归一化：从计数表到 CDF 累积数组

为什么要先 sort 再前缀和？ 因为 unordered_map 的迭代顺序是不确定的（哈希桶的排列），如果直接在这上面做前缀和，同一个模型、同一个 seed 下，CDF 数组里元素的顺序每次运行都可能不同，那 lower_bound 找到的边界就会漂移，破坏可复现性。显式按字符升序排序，把”迭代顺序不确定”这个隐患彻底消除——这是 CDF 采样能稳定复现的关键细节，也是新手最容易忽视的地方。

为什么返回 total 而不是直接在函数内保存？ 因为 total（总计数）在采样和概率展示里都要用到，而且它同时是”概率归一化”验证的对象。把它作为返回值，让调用方显式持有，比藏在某个字段里更容易追踪，也避免重复计算。

4.3 加权随机采样：轮盘赌 + 二分

为什么随机数范围是 [1, total] 而不是 [0, total-1]？ 这是为了和 CDF 的语义对齐。CDF 里每个元素 (ch, cum) 的 cum 是”到 ch 为止的累积计数”，第一个字符的 cum 就是它的计数本身。如果从 [1, total] 取 r，lower_bound 找第一个 cum >= r，那么：

  • r 落在 [1, cum_1] → 选第 1 个字符（其概率 = cum_1/total）
  • r 落在 (cum_1, cum_2] → 选第 2 个字符（其概率 = (cum_2-cum_1)/total）
  • 依此类推……

恰好每一段长度正比于对应字符的计数，采样正确。如果用 [0, total-1]，第一个字符对应的区间会被错误地缩短一个，边界字符的概率就会系统性偏低。

为什么用自定义比较器 p.second < val？ 因为 lower_bound 默认对 pair<char,long long> 按 first（char）比较，但我们要按 second（累积计数）比较。必须显式传 lambda，否则二分的就是 char 的字典序，结果完全错误。这是 C++ 里 lower_bound 用于非默认排序容器时的经典坑。

4.4 生成：滑动窗口驱动的状态转移

ctx = out.substr(out.size() - (n-1)) 为什么是 out.size() - (n-1)？ 因为新的上下文应该是”输出最后 n-1 个字符”。out.size() 是当前输出长度，减去 (n-1) 就是最后 n-1 个字符的起始下标。比如 n=3（上下文 2 个字符），out 当前是 "the"（长度 3），out.size() - 2 = 1，substr(1) = "he"，正是我们想要的”新上下文 = 输出末尾 2 字符”。

这里要特别警惕一个思维陷阱：很多人会想当然地把新上下文写成 out.substr(0, n-1)（取开头）或者 out.substr(out.size() - n)（多取了一个字符）。前者会让上下文永远停在开头的 seed 上，完全不转移，生成内容会反复横跳；后者会让上下文多包含一个已经生成过的字符，状态错位。这两种错误都不会让程序崩溃，生成出来的文本”看起来”甚至可能还是通的——只有”生成文本每个 N-gram 都在模型里”这条验证才能真正抓到它。

4.5 困惑度：Laplace 平滑下的平均负对数似然

p = (count + 1.0) / (total + V) 这个式子为什么是 add-1 平滑？ 它给分子加 1（每个字符预支 1 个虚拟计数），分母加 V（词表里 V 个字符各预支一个），保证即使 count=0（未见过的 (ctx,next)），概率也是 1/(total+V) 而非 0。这样 log(p) 永远是有限的，交叉熵不会被零概率炸成无穷大。

为什么要显式处理 it == model.end()（上下文不在模型里）？ 因为我们是对整个语料（包括训练时已经见过的所有窗口）重新算概率。理论上每个语料窗口的上下文都应该在模型里，但为了稳健性（防止边界或未来改代码时的 off-by-one），还是做了 it == model.end() 时的兜底：此时 total=0, count=0，平滑后概率是 1/V（均匀假设），交叉熵会是 log V，虽然偏高但不至于崩溃。这个防御性检查是”量化验证”哲学的一部分——宁可给一个偏保守的指标，也不让程序在边界上崩掉。

⑤ 踩坑实录

这一节把开发过程中真实踩过的坑——症状 → 错误假设 → 真实原因 → 修复方式——完整记录下来，让读者能避开同样的坑。

坑 1：CDF 采样可复现性被 unordered_map 迭代顺序破坏

  • 症状：同样 seed=12345，程序连跑两次，生成的文本不一样；但单次运行内部，三次 generate 调用（同 seed）结果又是一致的。这种”跨运行不一致、运行内一致”的现象很反直觉。
  • 错误假设：以为 unordered_map 的迭代顺序是稳定的，直接在它的迭代器上做前缀和生成 CDF。
  • 真实原因：unordered_map 的桶顺序由哈希函数和插入历史决定，不同运行时进程的内存布局、哈希 seed 可能不同，导致桶顺序不同。于是 CDF 数组里字符的排列顺序在每次运行间漂移，lower_bound 找到的边界也随之漂移，采样结果自然不一致。
  • 修复方式：在 normalize() 里先把 CountMap 拷贝到 vector 并 sort（按字符升序），再在这个有序的 vector 上做前缀和。这样无论底层哈希如何，CDF 的顺序都是确定的，可复现性得到保证。

坑 2：显示代码误用累积计数当分子，概率”看起来”没归一化

  • 症状：打印 “th” 的转移概率时，得到 0.1 / 0.2 / 1.0，最后一个恰好是 1.0，让人误以为”我的归一化写错了，概率和超过 1 了”。
  • 错误假设：以为 normalize() 返回的 cdf vector 里存的是原始计数，可以直接拿来当分子。
  • 真实原因：cdf 里存的是累积计数（前缀和），最后一个元素恰好等于 total，所以最后一个字符的”概率”显示为 total/total = 1.0，其余的是累积值除以 total，看起来像一串递增的”概率”。
  • 修复方式：展示概率时遍历原始 counts（各字符的真实计数）除以 total，而不是遍历 cdf。教训：累积量和原始量不可混用，二者语义不同但类型相同（都是 pair<char,long long>），编译器帮不了你，只能靠独立验证兜底。

坑 3：滑动窗口取字符写成了取开头，状态不转移

  • 症状（这个是”险些犯”的坑，最终靠正确认识避开了，但值得记录）：上下文更新如果写成 out.substr(0, n-1)，生成的文本会在 seed 附近反复横跳，产生大量重复片段。
  • 错误假设：以为”上下文就是输出最前面的 n-1 个字符”（混淆了”窗口起点”和”窗口终点”）。
  • 真实原因：N-Gram 的上下文应该是”紧邻下一个待预测字符的前面 n-1 个字符”，即输出末尾的 n-1 个；取开头的话，上下文永远不随生成推进，模型永远从同一个状态反复采样，必然产生重复。
  • 修复方式：明确写 ctx = out.substr(out.size() - (n-1))，并在脑子里反复确认”新上下文 = 输出末尾 n-1 个字符”这个语义。配合 [Verify 4]（生成文本每个 N-gram 都在模型里）做自动化兜底。

坑 4：困惑度被零概率炸成 -inf 再变 NaN

  • 症状：不加平滑时，如果某个 (ctx, next) 在训练语料里没出现，log(0) 得到 -inf，累加后交叉熵变 +inf，exp(inf) 弹 NaN。
  • 错误假设：以为训练语料足够覆盖所有测试时可能出现的组合，不会出现零概率。
  • 真实原因：训练集和测试集（哪怕就是同一个语料）里，某些 (ctx,next) 组合只出现一次或完全不出现是常态，MLE 的”数数”公式对未见组合天然返回 0。
  • 修复方式：引入 Laplace（add-1）平滑，p = (count+1)/(total+V)，保证概率恒为正，交叉熵有限。这是语言模型的标准做法，也是本系列强调”量化验证要稳健”的体现。

6.1 困惑度的意义：一个值得展开的指标

困惑度 7.97 这个数字，单独看没有意义，但放在对比中意义就清晰了：

模型 困惑度（理论/实测） 含义
完美预测（知道答案） 1.0 下界，每步都对
本文 trigram（Laplace 平滑） 7.97 学到了局部规律
均匀随机（瞎猜） ≈27 等于词表大小，无学习
unigram（只看单字符频率） 会更高，趋近词表 忽略了上下文

这个表说明了困惑度的锚点：1 是完美，V 是瞎猜，我们的 7.97 明确落在”学到了东西”的区间。如果某天你把代码改坏了（比如滑动窗口写成取开头导致上下文失效），困惑度会明显飙升、趋近 V，这条验证就会 FAIL，立刻暴露问题。这就是”数字不能撒谎”在工程里的价值。

⑦ 总结与延伸

7.1 技术局限性：马尔可夫假设的代价

马尔可夫链 N-Gram 模型最大的局限，恰恰来自它最核心的假设——马尔可夫性。真实语言的依赖是长程的：一个句子开头的”虽然”可能在十几个字之后才呼应一个”但是”，主语和谓语可能隔着很长的修饰从句。trigram 只能看前两个字符，bigram 只能看前一个，这种局部视野让它无法捕捉语法结构、语义一致性、事实逻辑。

生成样本里的 “rembe quick brown fox” 就是活生生的例子：局部 trigram 全都合法（”be “→”q”→”qu” 的转移在语料里都是真的），但拼出来的词根本不存在。模型”学会了字母搭配”，却”没学会单词边界和语义”——这正是 N-Gram 模型的边界。

7.2 局限带来的直接后果：维度灾难

增大 N 能缓解长程依赖的问题，但会撞上维度灾难：上下文空间大小是 V^(N-1)，随 N 指数增长。要可靠估计每个上下文下的转移分布，需要的训练数据也随 N 指数增长，否则语料会稀疏到”每个上下文只出现一次”，模型退化成死记硬背，泛化能力反而更差。这解释了为什么实际产品里 N 通常只取 2~5，而不是 100。

7.3 可继续优化的方向

  • 更高级的平滑：add-k、Good-Turing、Kneser-Ney 等平滑方法，比 add-1 在稀疏语料下的估计更准。Kneser-Ney 尤其被证明在很多场景下优于其他方法。
  • 回退（backoff）与插值（interpolation）：当高阶 N-gram 稀疏时，回退到低阶 N-gram 的概率估计（P(trigram) 如果见过否则 P(bigram) 否则 P(unigram)），这是经典 Jelinek-Mercer 插值的思想。
  • 词级而非字符级：用词 token 而非字符 token，能天然捕捉”单词边界”这个语义单元，生成文本会更通顺（但词表变大，稀疏问题更严重）。
  • 与神经网络结合：N-Gram 的稀疏离散分布，可以输入神经网络做特征，或作为 RNN/LSTM/Transformer 的”热身”先验。

7.4 与本系列的关联

本文是”每日编程实践”系列里第一篇概率语言模型，但它和系列里大量算法主题一脉相承：

  • 与 DBSCAN/GMM 聚类（06-22、06-23）一样，核心都是”用统计分布描述数据规律”；
  • 与 Huffman 编码（08-12）一样，都是”从数据里统计频率、再据此做预测/压缩”；
  • 与 Kalman Filter/EKF（09-23、09-24）一样，都在处理”给定历史，预测未来”这个根本问题，只是马尔可夫链是离散状态空间的”零阶/一阶”版。

更深一层看，本文强调的”用困惑度这类客观指标代替主观观感“，贯穿了整个系列的创作理念——从最早的像素均值/标准差验证，到后来的 PSNR/加速比/精确匹配，数字永远比眼睛可靠。

附：采样分布正确性的统计验证（大数定律视角）

前面五个验证器都是”结构层面”的正确性（归一化、可复现、合法 N-gram、困惑度），但还差一个”统计层面”的验证：采样器到底有没有真的按训练出来的概率在采样？ 这个问题用一次采样是看不出来的——就像抛硬币，抛一次是正面不代表正反概率各 50%。正确的方法是大量采样，用频率逼近概率。

大数定律（Law of Large Numbers）告诉我们：当采样次数 N 足够大时，事件发生的频率会收敛到它的真实概率。所以正确的验证思路是：

  1. 选一个已知真实分布的上下文，比如 “th”，它在语料里 P('e')=0.8, P('a')=0.1, P(' ')=0.1。
  2. 用采样器在这个上下文下采样 100 万次。
  3. 统计 ‘e’、’a’、’ ‘ 各自出现的频率，与真实概率对比。
  4. 断言：|频率 - 概率| < 0.01（1% 的容差，足以区分”正确采样”和”均匀乱猜”）。

这个验证如果做，应该能通过，因为它检验的正是 sample() 里 CDF+二分的正确性。它和 [Verify 3]（可复现性）互补：Verify 3 保证”确定性”，这个验证保证”分布正确性”——一个确定性但分布错误的采样器，能通过 Verify 3，却过不了这个频率检验。

为什么这个验证如此关键？ 因为 CDF 采样是全文最容易”悄悄出错”的地方：lower_bound 的比较器写反、随机数范围写错 [0, total) 而非 [1, total]、CDF 忘了排序，这些错误都不会让程序崩溃，甚至可能让几次采样的结果”看起来没问题”，只有大规模频率统计才能稳定地抓住它们。这再次呼应了本系列的核心信条：不要太相信眼睛，要让数字说话。

附：为什么用 mt19937_64 而不是 rand()

熟悉 C 的读者可能会问：为什么不用更简单的 rand() % total？这里有两个必须用 mt19937_64 + uniform_int_distribution 的理由：

  1. rand() % total 有模偏差（modulo bias）：rand() 的上界 RAND_MAX 通常不是 total 的整数倍，取模后，较小的余数会被映射到更多个原始值上，导致分布轻微不均。对 total 很大的情况这个偏差不可忽略。uniform_int_distribution 内部做了拒绝采样，保证 [1, total] 上的均匀性是无偏的。

  2. rand() 的随机性质量差：不同平台 rand() 的实现不同且质量参差，周期短，统计性质差。mt19937_64 是 64 位梅森旋转，周期 2^19937-1，通过了大量统计随机性检验，是 Monte Carlo / 采样类算法的事实标准。

对文本生成这种”每次采样都要跑”的场景，随机数发生器的质量直接影响生成文本的分布正确性。一个带模偏差的采样器，短期看不出问题，长期会让某个字符的出现概率系统性偏高——这恰恰是”用频率验证”能暴露、而”用眼睛看一次生成”暴露不了的隐患。

附：从字符到词——一个自然的下一步

本文实现的是字符级（character-level）trigram。如果把它改成词级（word-level），只需要把”字符”替换成”词 token”，训练时用分词后的词序列，生成时逐词采样。词级模型的优势是天然捕捉到”单词”这个语义单元，生成的文本不会有 “rembe” 这种跨词拼凑的假词；代价是词表 V 急剧增大（常见英文词表达数万），稀疏问题暴增，对平滑和回退的需求更高。

这个”字符级 vs 词级”的权衡，其实是大模型里”子词切分（subword tokenization，如 BPE）”的伏笔：BPE 正是取两者之长，用高频子词单元兼顾词表大小和语义捕捉。理解了 N-Gram 的这一层，就为理解现代 tokenizer 埋下了种子。

附：为什么困惑度要取 exp 而不是直接看交叉熵

最后澄清一个常见的疑惑：交叉熵已经是平均负对数似然（越小越好），为什么还要多此一举地算 perplexity = exp(cross_entropy)？

答案是：exp 把”对数域”拉回”线性域”，让数值有了直观的物理意义。交叉熵 2.99 bits，这个”2.99 个比特”很难直接体会；但困惑度 7.97 可以被直观理解成”模型平均在 8 个选项里犹豫”。对人的直觉来说，指数映射后的认知负担远小于对数域。这也是为什么所有语言模型论文都报困惑度而非交叉熵——它更贴近”预测难度”这个人类可感的量。

举例：如果模型的交叉熵是 0（完美预测），困惑度就是 exp(0)=1，对应”每次都十拿九稳”；如果交叉熵是 log(27)（均匀瞎猜 27 个字符），困惑度就是 27，对应”完全抓瞎”。困惑度把这条从 1 到 V 的”难度标尺”线性摊开了，读起来一目了然。

最终总结：本文用约 150 行 C++ 实现了一个完整的字符级 trigram 马尔可夫链文本生成器，并用五个结构验证器加一个统计验证思路，把这个”生成文本”的经典问题，从”看起来像不像”的主观判断，提升到了”概率归一化、可复现、合法 N-gram、困惑度定量”的客观标准。马尔可夫链是理解一切语言模型的起点，而”用数字说话”是贯穿本系列每一篇文章的方法论。
